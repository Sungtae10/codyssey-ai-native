## 마지막 자기 점검 4문항

제출 전에 소리 내어 답해 본다. 막히면 그 부분이 심사에서 막힌다.

1. **"두 구현이 같다는 걸 어떻게 증명하나요?"**
   → 5개 계약을 먼저 고정했고, 같은 시트·같은 9열에 `도구` 열만 달리해 적재했습니다. 실시간 피드라 입력 집합이 달라져서 **검증 단위를 집계에서 레코드로 내렸고**, 같은 기사 7건에서 점수가 7/7 일치했습니다. 불일치 1건(후행 쉼표)도 원인과 함께 기록했습니다.

2. **"θ=2는 왜 2인가요?"**
   → 가중 2단 사전에서 θ=2는 "T1 1개 또는 T2 2개"를 뜻합니다. v1의 평면 사전은 실제 코퍼스에서 CORE가 0건이라 폐기했고, 재설계 후 Node.js 단위 테스트로 CORE 약 20%를 확인한 뒤 도구에 넣었습니다. 실측은 Make 19% / n8n 18%로 예측과 일치했습니다.

3. **"검증 등식이 뭔가요?"**
   → `CORE 건수 + REF 건수 = 필터 통과 건수` 입니다. **이 등식 하나가 Make의 Fallback route 34건 유실과 n8n Switch의 9건 유실을 각각 잡아냈습니다.** 둘 다 오류 없이 "성공"으로 표시됐기 때문에 등식이 없었으면 발견하지 못했습니다.

4. **"프로젝트 2는 왜 Make인가요?"**
   → 이 업무의 실패는 느림이 아니라 **관측 공백**이라 24/7 가동이 곧 요구사항입니다(비교 항목 ⑧). n8n 로컬은 터미널을 닫으면 정지합니다. 여기에 실행 로그로 사전을 개선해야 한다는 점(⑤), 활성 시나리오 2개를 P1+P2로 소진하도록 설계한 점(③)을 더했습니다.
