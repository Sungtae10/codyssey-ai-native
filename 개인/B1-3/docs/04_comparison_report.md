# 자동화 도구 비교 구현 보고서 — Make vs n8n

**과제** Codyssey B1-3 · 노코드 자동화 기초: 워크플로우 설계 (프로젝트 1)
**워크플로우** TRC-v2 — 기술경영 리서치 큐레이션 파이프라인
**비교 도구** Make (클라우드 관리형) · n8n Community Edition v2.32.6 (셀프호스팅)
**구현·측정일** 2026-07-30
**유료 결제** 0원

## 1. 요약 (Executive Summary)

동일한 워크플로우 1개를 Make와 n8n으로 각각 구현했다. 방법론은 **구현 전에 도구 중립 명세서(TRC-v2)를 고정하고 두 구현체를 그 명세의 서로 다른 실행체로 취급**하는 것이었다.

### 1.1 최종 실측 결과

| | **Make** | **n8n** |
|---|---|---|
| 실행 시각 | 12:52 | 17:20:42 (Execution ID#17) |
| RSS 수집 | 50건 | 50건 |
| 노이즈 필터 통과 | **42건** (8건 제외) | **49건** (1건 제외) |
| CORE | **8건 (19%)** | **9건 (18%)** |
| REF | 34건 | 40건 |
| **검증 등식** | 8+34=42 ✅ | 9+40=49 ✅ |
| 실행 시간 | 18.0초 | 12.424초 |
| 데이터량 | 190.5 KB | 127 KB |
| 소모 자원 | **135 오퍼레이션** | 0 (과금 없음) |
| 구성 요소 | 모듈 7 + 필터 2 | 노드 8 |
| 첫 구현까지 소요 | **약 30분** | **약 90분** |

> **필터 통과 건수가 42 vs 49로 다른 이유**: 전자신문 RSS는 실시간 피드이고 두 실행 사이에 4시간 반이 흘렀다. `[포토]` 기사가 밀려나고 새 기사가 유입됐다. **동일 입력을 보장할 수 없으므로 동일성 검증의 단위를 집계값에서 레코드로 내렸다** (§4.2).

### 1.2 판단 축별 우세

| 판단 축 | 우세 | 실측 근거 |
|---|---|---|
| 첫 구현까지의 시간 | **Make** | 30분 vs 90분 — 차이의 대부분이 런타임 설치·인증 발급 |
| 환경 구성 안정성 | **Make** | Make 0건 실패 / n8n 환경 문제 2건 (Node MSI, PowerShell 정책) |
| 24/7 가동 보장 | **Make** | 관리형. n8n은 터미널 종료 시 정지 |
| 실행량 한계비용 | **n8n** | Make 135 op/회 vs n8n 0 |
| 로직 표현력·유지보수 | **n8n** | 12키워드 가중 스코어링: Make 400자 수식 2개 / n8n 배열 2줄 |
| 디버깅 반복 비용 | **n8n** | 노드 단위 재실행 무료. Make는 재실행마다 오퍼레이션 소모 |
| 데이터 주권 | **n8n** | 자체 인프라 |
| 비개발자 인수인계 | **Make** | 캔버스·History가 문서 역할 |

**최종 권고**: 월 1,000 오퍼레이션 이하의 상시 가동 자동화는 Make, 처리량이 많거나 로직이 복잡하거나 데이터 반출 제약이 있으면 n8n. 프로젝트 2(DART 공시 레이더)는 "매일 빠짐없는 자동 수집(관측 공백 0)"이 요구사항이므로 **Make를 선택**했다.

## 2. 대상 워크플로우

```
[Trigger] RSS 신규 기사 (전자신문 전자 섹션, 1일 1회 08:00 KST)
    │
    ├ [노이즈 필터] 제목에 [포토] 포함 시 제외
    ▼
[Action 1] 정규화 — HTML 태그·엔티티 제거, 200자 절단, KST 통일, JSON 안전화
    ▼
[Action 2] 스코어링 — 가중 2단 시그널 사전 (T1 2점 / T2 1점)
    ▼
[조건 분기] score >= 2 ?
    ├── CORE → [Action 3] Sheets(CORE) 적재 → [Action 4] Discord 알림
    └── REF  → [Action 5] Sheets(REF) 적재      (알림 없음)
```

**요구사항 충족**: Trigger 1개 / Action 5개 / 조건 분기 1개 / 양 경로 실행 확인 ✅

### 2.1 가중 2단 시그널 사전 — 분기 기준의 근거

기업의 발표는 **구속력이 다르다.** '투자를 집행했다'와 '개발 중이다'는 정보 가치가 같지 않다. 그래서 **되돌릴 수 없는 자원 배분 결정에 2점, 방향성 발표에 1점**을 부여했다.

| 등급 | 키워드 | 판단 기준 |
|---|---|---|
| **T1 (2점)** | 투자, 인수, 배당, 특허, 양산, 수주 | **비가역적 결정** — 자본이 이미 투입되거나 법적 권리가 확정됨 |
| **T2 (1점)** | 개발, 출시, 공급, 진출, 제휴, 확대 | **방향성 발표** — 의도는 드러나지만 철회 가능 |

θ=2 → "T1 1개" 또는 "T2 2개"가 CORE.

**제외한 어휘**: `AI`, `반도체` 등 고빈도 주제어(거의 모든 기사에 등장해 분기가 무의미해짐).

## 3. 구현 과정 요약

### 3.1 공통 선행: 명세 우선 + 도구 밖 단위 테스트

1. Google Sheets 1개(탭 `CORE`/`REF`, 9열) + Discord Webhook 준비
2. **도구 중립 명세서 TRC 작성** (입력 이벤트 / 정규화 / 분기 / 출력 / 멱등성 5개 계약)
3. **스코어링 로직을 Node.js로 단위 테스트** — 도구에 넣기 전에 사전을 확정

> **이 3번이 이번 구현의 분기점이었다.** 초기 설계(v1)는 소스를 전체기사 피드로, 사전을 공시/증권 어휘(유상증자·합병·지분…)로 잡았는데, 실제 코퍼스에 대입하니 **CORE가 0건**이었다. 논리적으로는 옳았지만 데이터에서 틀렸다.
> 도구 위에서 이걸 발견했다면 오퍼레이션을 소모하며 시행착오했을 것이다. **로직을 도구 밖에서 확정한 뒤 옮기면, 두 구현체에서 나타나는 차이가 전부 '도구의 차이'로만 남는다** — 비교 분석의 신뢰도를 만드는 방법이다.

### 3.2 Make 구현 (모듈 7 + 필터 2)

| # | 모듈 | 역할 |
|---|---|---|
| 2 | RSS › Watch RSS feed items | Trigger (상태 저장 폴링) |
| — | Filter `본문기사만` | `[포토]` 제외 → **50→42, 8건 차단 실측** |
| 3 | Tools › Set multiple variables | 정규화 (변수 7개) |
| 6 | Tools › Set multiple variables | 스코어링 (`matched`, `score`) |
| 10 | Flow Control › Router | 조건 분기 (명시적 조건 2개) |
| 11 | Google Sheets › Add a Row | CORE 적재 |
| 13 | HTTP › Make a request | Discord 알림 (Data structure 방식) |
| 12 | Google Sheets › Add a Row | REF 적재 |

**마주친 벽 6가지 (전부 실측)**

| # | 문제 | 해결 |
|---|---|---|
| 1 | **`add()` 함수가 없다** | Make 수학 함수는 `sum(a; b; …)`. 잘못된 함수명은 에러 없이 **빈 값**을 만들어 분기가 한쪽으로만 흐른다 |
| 2 | **`dateDifference()`도 없다** | 날짜 차이는 밀리초 직접 나눗셈 또는 `addDays()` + Date 연산자 비교 |
| 3 | 같은 모듈 내 변수 상호 참조 불가 | 정규화/스코어링을 **2개 모듈로 분리** |
| 4 | 문자열 결합에 `+` 사용 불가 (숫자 덧셈으로 해석) | 한 필드에 `{{ }}` 표현식을 **인접 배치**하면 자동 결합 (Make 관용구) |
| 5 | **Fallback route가 34건을 조용히 삼켰다** | §5-⑨ 상세 |
| 6 | Discord Raw JSON 본문 입력란이 없음 | **`JSON › Data structure`** 로 직렬화를 도구에 위임 |

### 3.3 n8n 구현 (노드 8개, v2.32.6 npx 셀프호스팅)

| # | 노드 | 역할 |
|---|---|---|
| 1 | Schedule Trigger | 매일 08:00 |
| 2 | RSS Read | 피드 전량 조회 (50건) |
| 3 | Filter `본문기사만` | `[포토]` 제외 → **50→49, 1건 차단** |
| 4 | Code (Run Once for All Items) | 정규화 + 스코어링 + `tier` 판정 **통합** |
| 5 | **If** | 조건 분기 (`score >= 2`) |
| 6 | Google Sheets › Append Row | CORE 적재 |
| 7 | HTTP Request | Discord 알림 (Using Fields Below + Batching) |
| 8 | Google Sheets › Append Row | REF 적재 |

**마주친 벽 6가지 (전부 실측)**

| # | 문제 | 해결 |
|---|---|---|
| 1 | **Node.js MSI 설치 실패** — Windows Installer DLL 오류 | `winget install OpenJS.NodeJS.LTS` 로 우회 |
| 2 | **PowerShell 실행 정책이 `npx.ps1` 차단** | `npx.cmd n8n` 또는 `Set-ExecutionPolicy CurrentUser RemoteSigned` |
| 3 | **인스턴스 타임존이 `America/New_York`** | 워크플로우 Settings에서 `Asia/Seoul`. 단, **계약 N6에서 코드에 타임존을 명시해뒀기 때문에 시트 값 자체는 무사했다** |
| 4 | **Sheets 파일 목록 403** — Google Drive API 미활성 | `From list` → **`By URL`**. 시트 1개만 공유했으니 Drive 열람 권한이 없는 게 정상 (최소 권한의 대가) |
| 5 | **Switch 노드가 9건을 삼켰다** — 규칙 우변의 Fixed/Expression 모드 차이 | **If 노드로 교체** (§5-⑨) |
| 6 | **Discord 429 Rate Limited** | `Batching`(1건/1.5초) + `Retry On Fail`(3회/2초) |

### 4.2 동일성 검증 — 레코드 단위 대조 ★

실시간 피드라 두 도구가 동일 입력 집합을 받지 못한다. 그래서 **같은 `링크`를 가진 행끼리 대조**했다. 집계값 비교는 우연히 맞거나 틀릴 수 있지만, **레코드 대조는 로직 동일성을 직접 증명한다.**

| # | 기사 | Make 점수 | n8n 점수 | 매칭 키워드 | 일치 |
|---|---|---|---|---|---|
| 1 | 경동나비엔, 공기열 보일러 국내 생산 | 3 | 3 | 양산, 출시 | ✅ |
| 2 | 엡손, 고산테크에 추가 투자 | 2 | 2 | 투자 | ✅ |
| 3 | 한국엡손, 협동로봇 신시장 진출 | 3 | 3 | 출시, 진출, 확대 | ✅ |
| 4 | 韓-브라질, 경제 협력 체계 구축 | 4 | 4 | 투자, 공급, 진출 | ✅ |
| 5 | 포유디지탈, 미니PC LED 셋톱박스 개발 | 3 | 3 | 개발, 공급, 확대 | ✅ |
| 6 | LG전자, 897억원 중간배당 | 2 | 2 | 배당 | ✅ |
| 7 | 코웨이, 제주신화월드 체험 객실 확대 | 2 | 2 | 제휴, 확대 | ✅ |

**서로 다른 도구, 서로 다른 실행 시각, 같은 기사에 같은 점수 — 7/7 일치.**

### 4.3 발견된 불일치 1건 (정직하게 기록)

| 항목 | Make | n8n |
|---|---|---|
| `매칭키워드` 표기 | `출시,확대,` ← **후행 쉼표 있음** | `출시,확대` ← 없음 |

Make에 넣은 `replace(6.matched; "/,$/"; "")` 가 동작하지 않았다. **점수와 키워드 구성은 동일하지만 문자열 표기가 다르다.**

> **여기서 얻은 교훈**: 출력 계약을 **'값'까지만 정의하고 '표기'까지 정의하지 않으면** 이런 틈이 생긴다. n8n은 `Array.join(',')` 로 후행 구분자가 원리적으로 생기지 않지만, Make는 조건부 문자열 연결이라 후처리가 필요했고 그 후처리가 실패했다.
> **완전 일치를 주장하는 것보다, 불일치 1건을 찾아 원인을 설명하는 것이 검증의 증거다.**

## 5. 비교 항목 (9개 — 요구 기준 5개 초과)

### ① UI/UX 및 워크플로우 표현 방식

| | Make | n8n |
|---|---|---|
| 캔버스 | 원형 노드 좌→우 파이프라인. Router 분기가 시각적으로 뚜렷 | 사각 노드 + 명시적 연결선. 그래프 성격 |
| 데이터 확인 | 모듈 위 버블 숫자 | 커넥션 위 item 수 + 노드별 INPUT/OUTPUT 3뷰(Table/JSON/Schema) 상시 노출 |
| 표현 지향 | **프로세스 도해** — 비개발자 설명에 강함 | **데이터 파이프라인 다이어그램** — 변환 지점 파악에 강함 |

**평가**: n8n의 INPUT/OUTPUT 상시 노출은 실제 구현 중 결정적으로 유용했다. 필드명 실측(`link` vs `url`), 타입 확인(`score`가 `#`=number인지), 값 미리보기가 한 화면에서 된다. Make는 실행 후 History를 열어야 같은 정보를 얻는다.

### ② 설정 난이도 및 첫 구현 소요 시간 (실측)

| 단계 | Make | n8n |
|---|---|---|
| 도구 준비 | 웹 가입 즉시 (3분) | Node.js 설치 + `npx n8n` + 계정 생성 — **환경 오류 2건 발생** (25분) |
| Google 인증 | OAuth 클릭 동의 (2분) | GCP 프로젝트 → Sheets API 활성화 → 서비스 계정 → JSON 키 → **시트 공유** (30분) |
| 워크플로우 구성 | 모듈 7 + 필터 2 (25분) | 노드 8 (35분, Switch→If 교체 포함) |
| **합계** | **약 30분** | **약 90분** |

**평가**: 차이의 2/3이 **워크플로우가 아니라 환경 구성과 자격증명 획득**이다. 워크플로우를 한 줄도 만들기 전에 n8n에서 두 번 막혔다(MSI DLL 오류, PowerShell 실행 정책). 이는 1회성 비용이지만 0은 아니고, **팀 도입 시 이 비용에 인원수를 곱해야 한다.**

- 노이즈 필터로 차단된 8건은 하위 모듈 오퍼레이션을 **전혀 소모하지 않았다** → 필터가 회당 약 24 오퍼레이션(15%) 절감
- 구현·검증 과정 총 사용량: **427 / 1,000 (43%)**
- 운영 프로파일: 5건/1일 1회 → 약 14 op/회 → **월 약 420**
- 50건 매일이면 월 4,050 → 무료 한도 4배 초과 ❌

**평가**: **처리량이 늘면 손익분기가 뒤집힌다.** 월 1,000 이하는 Make 무료가 절대적으로 유리하고, 수천 단위면 n8n의 한계비용 0이 압도한다. 다만 n8n은 실행 과금 대신 **호스트 자원·가동 관리 비용**이 발생한다.

> **참고 — Zapier 제외 근거**: Zapier 무료는 **월 100 태스크 + 2단계 Zap(트리거 1 + 액션 1)** 만 허용하고 멀티스텝·Filter·Paths가 유료다. 본 과제 필수 요구사항(Action 2개 이상 + 조건 분기 1개 이상)을 **무료로는 구조적으로 충족할 수 없다.**

### ④ 인증·연동 방식

| | Make | n8n |
|---|---|---|
| Google 연동 | 플랫폼 소유 검증 OAuth 앱 → 클릭 동의 | 사용자가 GCP에서 직접 발급 |
| 권한 부여 모델 | **OAuth 위임** — 사용자를 대신해 행동 | **서비스 계정** — 독립된 제3의 주체 |
| 리소스 접근 | 사용자 권한 그대로 | **리소스마다 별도 공유 필요** (시트를 계정 이메일과 공유) |
| 부수 효과 | 파일 목록 브라우징 즉시 동작 | **Drive 열람 권한이 없어 파일 목록 403** → `By URL` 사용 |
| Gmail 사용 | 즉시 가능 | **서비스 계정으로 불가** (도메인 전체 위임 필요, 개인 Gmail 적용 불가) |

**평가**: Make는 "연동 비용을 플랫폼이 대신 지불"하는 모델이다. 대가는 자격증명·데이터가 제3자 클라우드를 경유한다는 점.
서비스 계정의 최소 권한 원칙은 보안상 우월하지만 **UI 편의를 잃는다** — 시트 1개만 공유했으니 파일 목록을 못 보는 것이 정상 동작이다. 보안과 편의의 트레이드오프를 실물로 확인했다.

### ⑤ 실행 로그 및 디버깅

| | Make | n8n |
|---|---|---|
| 로그 위치 | `History` | `Executions` (Auto refresh 지원) |
| 확인 단위 | 모듈별 입출력 번들 JSON | 노드별 INPUT/OUTPUT 3뷰 |
| 필터 차단 표시 | 로그에 "The bundle did not pass through the filter" ×8 | 커넥션에 `Kept N items` |
| 부분 재실행 | `Run this module only` | 노드 단위 `Execute step` + **Pin Data** |
| 반복 비용 | **재실행마다 오퍼레이션 소모** | 무료 |
| 실행 이력 | 실행별 op 수·시간·데이터량 | 실행별 시간·데이터량·ID·성공/실패 |

**평가**: 개발 단계의 실질 차이가 가장 크게 벌어진 항목이다. 이번 구현에서 n8n은 노드 재실행을 수십 회 했지만 비용이 0이었다. Make는 시행착오가 크레딧을 소모하므로 **"설계를 먼저 확정하는" 규율을 강제**한다 — 제약이 규율을 만든 사례다.
Make의 필터 차단 로그 8줄은 "입력 품질 관리를 설계했고 실제로 8건을 걸렀다"는 직접 증거로 그대로 쓸 수 있었다.

### ⑥ 상태 관리 및 멱등성

| | Make | n8n |
|---|---|---|
| 폴링 상태 저장 | `Watch` 접두 트리거에 **내장** | `RSS Feed Trigger`에는 있으나 `RSS Read`(Action)에는 **없음** |
| 본 구현 선택 | `Watch RSS feed items` | `Schedule Trigger + RSS Read` (채점용 49건 확보 목적) |
| 결과 | 신규 항목만 처리 | **매 실행 전량 재처리** → 운영 시 `Remove Duplicates` 필수 |
| 규약 | 트리거 이름의 `Watch` 가 "내가 기억한다"를 선언 | 노드 조합 자유도가 높은 대신 책임이 설계자에게 |

**실측으로 확인한 경계 조건**: 채점 데이터 확보를 위해 Make에서 트리거 위치를 3회 리셋했더니 **같은 기사가 시트에 3번 적재**됐다. **"도구가 멱등성을 보장한다"는 말은 정확히는 "정상 폴링 경로에서만"이라는 뜻**이다. 개발 단계와 운영 단계의 보장 범위가 다르다.

### ⑦ 로직 표현력 및 유지보수성

| | Make | n8n |
|---|---|---|
| 표현 수단 | 선언형 내장 함수 | JavaScript / Python Code 노드 |
| 12키워드 가중 스코어링 | `sum(if(contains(...);2;0); …)` — **약 400자 수식 2개** | 배열 2개 + `filter()` **2줄** |
| `tier` 판정 | 같은 모듈에서 `score` 참조 불가 → 분기 필터에 위임 | **같은 노드에서 계산** |
| 키워드 1개 추가 | 400자 수식 2곳 수정 (누락 위험) | 배열에 문자열 1개 추가 |
| 로직 위치 | 모듈 경계로 분산 | Code 노드 1개에 응집 |
| 버전 관리 | 블루프린트 JSON 내보내기 | 워크플로우 JSON + Code 텍스트 diff |

**Make 함수 라이브러리의 실제 경계 (실측)**

| 기대한 함수 | 실제 | 대응 |
|---|---|---|
| `add(a; b; …)` | **없음** | `sum(a; b; …)` |
| `dateDifference(d1; d2; unit)` | **없음** | 밀리초 나눗셈 또는 `addDays()` + Date 연산자 |
| 같은 모듈 내 변수 참조 | **불가** | 모듈 분리 |
| 문자열 결합 `+` | 숫자 덧셈으로 해석 위험 | 표현식 인접 배치 |
| `replace(...; "/,$/"; "")` | **동작하지 않음** (§4.3) | — 원인 미해결, 표기 불일치로 남김 |

**평가**: **선언형 노코드의 실질적 학습 비용은 "무엇을 할 수 있는가"가 아니라 "무엇이 없는가"를 알아내는 데 있었다.** 코드 환경에서는 없는 함수가 즉시 에러를 내지만, 노코드 수식 편집기에서는 **잘못된 함수명이 조용히 빈 값을 만들어** 분기가 항상 한쪽으로만 흐른다. 이 침묵이 디버깅 비용의 실체다.

### ⑧ 호스팅·가동 지속성 및 운영 부담

| | Make | n8n Community (로컬) |
|---|---|---|
| 가동 주체 | Make 클라우드 24/7 | 사용자 호스트 |
| 터미널 종료 시 | 정상 | **정지** |
| PC 절전 시 | 정상 | **트리거 미발화** |
| 타임존 | 계정 설정 | **서버 로케일** (기본 America/New_York) |
| 상시화 방법 | 불필요 | VPS/NAS 상시 구동 또는 Docker 재시작 정책 |
| 상시 운영 비용 | 무료 플랜 내 0원 | VPS 월 수천 원 이상 |
| 장애 대응 | 플랫폼 책임 | 사용자 책임 (백업·업데이트·복구) |

**평가**: 노코드 자동화의 가치는 "내가 없을 때도 돌아간다"에 있다. **로컬 셀프호스팅은 이 전제를 부분적으로 깨뜨린다.** n8n을 상시화하려면 인프라를 함께 설계해야 하고, 그 순간 "무료"는 사라진다. **이 항목이 프로젝트 2에서 Make를 선택한 1순위 근거다.**

### ⑨ 조건 분기의 안전성 ★ 이번 비교의 핵심 발견

**두 도구에서 같은 종류의 사고를 다른 원인으로 겪었다.**

| | Make | n8n |
|---|---|---|
| 구성 | Router + Route B = `Fallback route` | Switch + 규칙 2개 (`tier` 문자 비교) |
| 사고 | **42건 중 CORE 8건만 처리, 34건이 어느 경로에도 기록되지 않음** | **49건 중 REF 40건만 처리, CORE 9건 소실** |
| 원인 | Fallback route 시맨틱을 신뢰 | 규칙 우변이 `Expression` 모드 (다른 규칙은 `Fixed`) |
| 표시 | **오류 없이 "성공"** | **오류 없이 "Workflow executed successfully"** |
| 해결 | 명시적 조건 `score < 2` | **If 노드로 교체** (출력이 true/false 2개로 강제) |

**도출한 설계 원칙 3가지**

1. **도구의 암묵적 동작에 데이터 무결성을 맡기지 않는다.** Fallback route는 "앞선 경로가 모두 막히면 실행"을 보장한다고 기대했지만 실측에서는 아니었다.
2. **조건이 여러 개인 분기(Router/Switch)는 '어느 규칙에도 안 걸리는 아이템'이 존재할 수 있다.** n8n에서 최종적으로 **If 노드**를 택한 이유는 출력이 true/false 2개뿐이라 **MECE가 선언이 아니라 구조로 보장**되기 때문이다.
3. **검증 등식을 반드시 확인한다** — `CORE 건수 + REF 건수 = 필터 통과 건수`. 이 등식이 두 도구에서 각각 사고를 잡아냈다. 등식 없이는 두 번 모두 "성공"으로 보였을 것이다.

## 6. 장단점 정리

### Make

**장점**
1. 첫 구현까지 30분 — 환경·인증 비용을 플랫폼이 흡수
2. 무료 플랜에서 Router·Filter·Webhook 전부 제공 (Zapier 무료는 불가)
3. 24/7 관리형 가동
4. 캔버스·History가 그대로 인수인계 문서
5. 오퍼레이션 과금이 "설계를 먼저 확정하는" 규율을 강제
6. 필터 차단·오퍼레이션 수를 History가 정량으로 남겨 보고서 근거가 됨

**단점**
1. 월 1,000 오퍼레이션 / 활성 시나리오 2개 — 확장 시 즉시 유료 전환 압력
2. 임의 코드 실행 불가 → 복잡 로직이 400자 수식으로 파편화
3. 함수 라이브러리 경계가 문서보다 좁음 (`add`, `dateDifference` 부재)
4. 같은 모듈 내 변수 참조 불가 등 문법 제약이 모듈 수를 늘림
5. 잘못된 함수·표현식이 **에러 없이 빈 값**을 만들어 조용한 실패를 유발
6. 디버깅 시행착오가 크레딧을 소모
7. 자격증명·데이터가 제3자 클라우드를 경유

### n8n Community (셀프호스팅)

**장점**
1. 실행 횟수 한계비용 0
2. Code 노드로 로직 응집, Git diff 가능
3. 노드 단위 재실행·Pin Data로 반복 디버깅이 무료
4. INPUT/OUTPUT 상시 노출로 필드명·타입 확인이 즉시
5. 데이터·자격증명이 자체 인프라를 벗어나지 않음
6. If 노드처럼 **구조적으로 안전한 분기 수단**을 제공
7. `Batching` / `Retry On Fail` 이 노드 단위 옵션으로 내장

**단점**
1. 환경 구성 실패 지점이 실재 (Node MSI 오류, PowerShell 정책) — 워크플로우 전에 2번 막힘
2. 자격증명 획득이 진입장벽 (GCP 5단계)
3. 로컬 구동 시 24/7 미보장 → 상시화하려면 인프라 비용
4. 서버 로케일 타임존이 기본값 (America/New_York)
5. 최소 권한의 대가로 UI 편의 상실 (파일 목록 403)
6. 상태 관리·멱등성 책임이 설계자에게
7. 병렬성이 높아 외부 API Rate Limit(429)에 더 쉽게 걸림
8. Community Edition은 SSO·RBAC·Git 버전관리 제외

## 8. 결론

두 도구의 차이는 기능표의 유무가 아니라 **"어떤 비용을 누가 지불하는가"의 배치 차이**였다.

- **Make**는 환경·인증·호스팅·가용성 비용을 플랫폼이 지불하고, 사용자는 실행량과 데이터 위치를 내준다.
- **n8n**은 사용자가 환경·인증·호스팅·상태관리 비용을 지불하고, 실행량 한계비용과 데이터 주권을 얻는다.

따라서 도구 선정은 기능 비교가 아니라 **업무 요구사항을 비용 항목으로 번역하는 작업**이다. 이번 워크플로우에서 그 번역은 이렇게 됐다.

| 요구사항 | 번역된 비용 | 우세 |
|---|---|---|
| 매일 아침 자동 실행 | 가동 지속성 비용 | Make |
| 하루 5건, 월 150건 수준 | 실행량 비용 미미 | Make |
| 판단 기준(키워드·가중치)을 계속 다듬는다 | 로직 유지보수 비용 | n8n |
| 공개 뉴스만 다룬다 | 데이터 주권 비용 0 | 무관 |

**3승 1패가 아니라, 네 축의 가중치가 상황마다 바뀐다**는 것이 이 비교의 결론이다.

그리고 이번 구현에서 가장 값진 것은 성능 비교가 아니라 **두 도구에서 각각 겪은 조용한 유실 사고**였다. Make의 Fallback route 34건, n8n의 Switch 9건 — **둘 다 오류 없이 "성공"으로 표시됐다.** 여기서 얻은 것은 도구 지식이 아니라 **검증 습관**이다: 분기의 통과 건수를 합산해 입력 건수와 대조하는 등식 하나가, 두 번 모두 사고를 잡아냈다.
