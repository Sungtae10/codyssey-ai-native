# TRC-v1 도구 중립 워크플로우 명세서
**Tool-Neutral Workflow Specification for "TechMgmt Research Curator"**

| 항목 | 내용 |
|---|---|
| 명세 ID | TRC-v1 (TechMgmt Research Curator v1) |
| 목적 | 기술경영 관점의 산업 뉴스를 자동 수집 → 전략 시그널 점수화 → 중요도 분기 → 아카이빙/알림 |
| 적용 대상 | 프로젝트 1 (Make 구현체 · n8n 구현체) |
| 작성 근거 | 평가 항목 2 "두 도구에서 동일성(입력 이벤트/핵심 Action/분기/최종 출력)을 맞추기 위해 어떤 설계 기준을 적용했는가" |

> **이 문서의 존재 이유**
> "같은 워크플로우를 두 도구로 만들었다"는 주장은 검증 가능해야 한다.
> 도구별 UI를 먼저 만들고 나중에 비교하면 "우연히 비슷한 것"이 되고, 심사자가 "어디까지 같은 건가"를 물었을 때 답이 흔들린다.
> 그래서 **구현 전에 도구와 무관한 계약(contract) 5개를 먼저 고정**하고, 두 구현체를 이 계약의 서로 다른 실행체로 취급했다.
> 계약이 같으면 동일 워크플로우이고, 계약을 지키는 방식의 차이가 곧 비교 분석 결과가 된다.

## 1. 계약 ① 입력 이벤트 계약 (Input Event Contract)

| 항목 | 규격 |
|---|---|
| 소스 | 전자신문 RSS — `https://rss.etnews.com/Section901.xml` |
| 형식 | RSS 2.0 (검증일 2026-07-26, `<item>` 25건 반환 확인) |
| 이벤트 1건의 정의 | 피드에 **직전 실행 이후 새로 등장한 `<item>` 1개** = 1 bundle / 1 item |
| 1회 실행당 최대 처리 건수 | **5건** (양 도구 동일 — 근거: 4.2절 오퍼레이션 예산) |
| 폴링 주기 | **1일 1회 08:00 KST** (양 도구 동일 — Make 무료·n8n Cloud 무료의 최소 인터벌이 15분이므로 15분 미만은 규격에서 제외) |
| 필수 입력 필드 | 제목, 링크, 발행일시, 요약 |

### 1.1 필드명 매핑 (도구별 출력 필드가 다름 → 규격 필드로 흡수)

| 규격 필드 | Make (RSS: Watch RSS feed items) | n8n (RSS Feed Trigger, `rss-parser` 기반) |
|---|---|---|
| 제목 | `title` | `title` |
| 링크 | `url` | `link` |
| 요약 | `summary` | `contentSnippet` → 없으면 `content` |
| 발행일시 | `dateCreated` (없으면 `dateModified`) | `isoDate` → 없으면 `pubDate` |

> ⚠️ **구현 시 반드시 실측할 것.** RSS 커넥터의 출력 필드명은 도구·버전에 따라 다르다.
> Make: RSS 모듈 우클릭 → `Run this module only` → 출력 번들에서 실제 키 확인
> n8n: RSS Feed Trigger → `Fetch Test Event` → OUTPUT 패널에서 실제 키 확인
> **이 실측 스크린샷 자체가 평가 항목 2의 근거 자료가 된다.**

## 2. 계약 ② 정규화 계약 (Normalization Contract)

두 도구가 서로 다른 문자열 처리 엔진을 쓰더라도 **동일 입력 → 동일 출력**이 되도록 규칙을 문자 단위로 고정한다.

| # | 규칙 | 정규식 / 처리 | 이유 |
|---|---|---|---|
| N1 | HTML 태그 제거 | `<[^>]*>` → 공백 | etnews `description`이 CDATA + `<p>` 태그 포함 |
| N2 | HTML 엔티티 제거 | `&[a-zA-Z#0-9]+;` → 공백 | `&nbsp;` `&quot;` 등이 점수 계산을 오염 |
| N3 | 연속 공백 정리 | `\s+` → 공백 1개, 앞뒤 trim | N1·N2가 남긴 공백 흡수 |
| N4 | 요약 길이 제한 | 앞 **200자** | Sheets 셀 가독성 + 점수 계산 대상 범위 고정 |
| N5 | JSON 안전화 (`title_safe`) | `["\\\r\n]` (ASCII 큰따옴표·백슬래시·개행) → 공백 | Discord Webhook 페이로드가 JSON이므로 제목의 ASCII 큰따옴표가 페이로드를 깨뜨림 |
| N6 | 시각 표기 | `YYYY-MM-DD HH:mm`, **Asia/Seoul 고정** | RSS `pubDate`는 `+0900`, Make/n8n 서버는 UTC → 표기 통일 없으면 두 시트의 값이 달라짐 |
| N7 | 빈 값 처리 | 요약이 없으면 빈 문자열, 점수 계산은 제목만으로 수행 | null 전파로 인한 분기 오판 방지 |

### 2.1 표준 출력 레코드 (양 도구 공통)

| 키 | 타입 | 예시 |
|---|---|---|
| `collected_at` | string | `2026-07-26 16:41` |
| `tool` | string | `Make` \| `n8n` (구현체별 하드코딩) |
| `tier` | string | `CORE` \| `REF` |
| `score` | number | `3` |
| `matched_keywords` | string | `투자,계약,협력` |
| `title` | string | `울산 글로벌 산업AX 선도도시 추진…` |
| `title_safe` | string | N5 적용본 (알림 페이로드 전용) |
| `summary` | string | 200자 이내 |
| `published_at` | string | `2026-07-26 09:10` |
| `link` | string | `https://www.etnews.com/...` |

## 3. 계약 ③ 분기 계약 (Branch Contract)

### 3.1 시그널 키워드 사전 (고정 12개)

기술경영 관점에서 "전략적 의사결정 시그널"에 해당하는 어휘만 4개 범주로 선별했다.
단순 빈발어(예: 'AI', '반도체')를 넣지 않은 이유는 **주제 필터가 아니라 의사결정 시그널 필터**를 만드는 것이 목적이기 때문이다.

| 범주 | 키워드 | 기술경영 프레임 |
|---|---|---|
| 자본시장 시그널 | 투자, 인수, 합병, 지분, 상장 | 기업 지배구조·자본 배분 변화 |
| 기술자산 시그널 | 특허, 양산, 출시 | 기술의 사업화 단계 이동 |
| 제도·정책 시그널 | 규제 | 외부 제약조건 변화 |
| 사업화 시그널 | 계약, 수주, 협력 | 밸류체인·파트너십 재편 |

### 3.2 판정 규칙

```
haystack = lower( title(N1~N3) + " " + summary(N1~N4) )
score    = SIGNAL 12개 중 haystack에 1회 이상 등장하는 "고유 키워드 개수"   (0 ~ 12)
θ (임계값) = 2

Route A (CORE) :  score >= 2
Route B (REF)  :  score <  2      ← 폴백 경로로 지정
```

- **중복 카운트 금지**: 같은 키워드가 3번 나와도 1점. 기사 길이가 점수를 좌우하지 않게 하기 위함.
- **θ=2의 근거**: θ=1이면 '협력' 같은 범용어 1개로 CORE가 되어 CORE 비중이 과다해지고, θ=3이면 실측 표본에서 CORE가 0건이 되는 구간이 발생했다. 실측 5건 표본에서 θ=2일 때 **CORE 2 / REF 3** 으로 두 경로가 모두 발화한다(4.1절).
- **MECE 보장**: 두 조건은 상호배타·전수이므로 유실이 원리적으로 0이다. 여기에 더해 도구 레벨에서도 이중 안전장치를 둔다 — Make는 Route B를 **Fallback route**로, n8n은 Switch의 **Fallback Output**을 REF로 지정한다. 필터 표현식에 오타가 나도 데이터가 사라지지 않는다.

## 4. 계약 ④ 출력 계약 (Output Contract)

### 4.1 Google Sheets (공동 저장소)

스프레드시트 **1개**를 두 도구가 공유하고, 시트 탭 2개(`CORE`, `REF`)를 쓴다.
`도구` 열로 구현체를 구분한다. → **같은 스키마에 두 도구의 결과가 나란히 쌓이는 것 자체가 "동일 워크플로우" 증빙**이 된다.

| 열 | A | B | C | D | E | F | G | H | I |
|---|---|---|---|---|---|---|---|---|---|
| 헤더 | 수집시각 | 도구 | 분류 | 점수 | 매칭키워드 | 제목 | 요약 | 발행일 | 링크 |

### 4.2 Discord 알림 (Route A 전용)

고정 템플릿 — 양 도구가 **바이트 단위로 같은 문자열**을 만들어야 한다.

```
🔎 [CORE] {title_safe}
· 점수 {score} / 시그널 {matched_keywords}
· 발행 {published_at} · 수집 {tool}
{link}
```

- **Route B는 알림 없음.** 의도적 설계다. 알림 채널의 가치는 신호/잡음 비율이므로, 참고 등급까지 알리면 채널이 무력화된다. 참고 등급은 시트에만 축적하고 주간 단위로 되돌아본다(→ 프로젝트 2와 연결).

## 5. 계약 ⑤ 멱등성 계약 (Idempotency Contract)

| 항목 | 규격 |
|---|---|
| 중복 판정 키 | `link` (RSS `guid`보다 안정적 — etnews는 `guid`가 URL과 동일하나 매체별로 형식이 달라짐) |
| 보장 방식 | **폴링 트리거의 상태 저장 기능에 위임** — Make `Watch RSS feed items`, n8n `RSS Feed Trigger` 모두 마지막 처리 지점을 인스턴스에 저장한다 |
| 재실행 시 | 같은 `link`가 두 번 적재되면 계약 위반 → 시트에서 `link` 중복 여부로 검증 |

> **이 계약이 도구 비교의 핵심 발견 하나를 만든다.**
> Make는 `Watch` 접두 트리거가 상태 저장을 내장하지만, n8n에서 `Schedule Trigger + RSS Read` 조합으로 만들면 상태가 없어 매 실행마다 전량 재적재된다.
> 즉 **동일 계약을 지키기 위해 n8n에서는 반드시 `RSS Feed Trigger`를 써야 하고**, `Schedule + RSS Read`로 대체하려면 `Remove Duplicates` 노드를 추가해야 한다. → 비교 분석 보고서 §5-⑥ 항목.

## 6. 오퍼레이션 예산 (무료 플랜 준수 설계)

Make 무료 플랜은 **월 1,000 크레딧 / 활성 시나리오 2개 / 최소 인터벌 15분**이다. 모듈이 번들 1개를 처리할 때마다 1 오퍼레이션이 소모되고, **트리거는 반환 데이터가 없어도 1 오퍼레이션이 계상**된다. 따라서 "최대 처리 5건 / 1일 1회"는 취향이 아니라 예산 제약에서 역산한 값이다.

| 구성 | 1회 실행 오퍼레이션 | 월 소모 (30일) |
|---|---|---|
| 트리거 | 1 | 30 |
| 정규화 Set (5건) | 5 | 150 |
| 스코어링 Set (5건) | 5 | 150 |
| Sheets 적재 (5건) | 5 | 150 |
| Discord (CORE 2건 가정) | 2 | 60 |
| **합계** | **18** | **540** |

- 잔여 460 크레딧을 **프로젝트 2(Make)** 에 배정 → 활성 시나리오 2개 = 무료 한도 정확히 소진.
- 10건/15분 간격으로 돌리면 월 2,880 오퍼레이션 초과 → 무료 플랜 불가. **이 계산이 "왜 5건·1일 1회인가"의 답이다.**
- n8n Community(셀프호스팅)는 실행 횟수 과금이 없으므로 이 제약을 받지 않는다. → 비교 분석 보고서 §5-③ 항목.

## 7. 실측 검증 결과 (스코어링 로직 단위 테스트)

`workflows/_test_scoring.js` 를 Node.js로 실행해 계약 ②③을 사전 검증했다. (실제 etnews 피드에서 확인된 5건 형태의 픽스처 사용)

```
[CORE] score=3 kw=투자,계약,협력 | 울산 글로벌 산업AX 선도도시 추진…
[REF ] score=0 kw=-             | 스리랑카, 군용 드론 동원해 모기 '소탕'…
[REF ] score=0 kw=-             | 유인원도 긴장하면 서로 끌어안아…
[CORE] score=3 kw=양산,계약,협력 | 정의선·젠슨 황, 한달만에 재회…
[REF ] score=1 kw=규제           | 李대통령, 방미 성과 9500억달러…

CORE=2 / REF=3   → 두 경로 모두 발화: true
```

JSON 안전화(N5) 검증 — ASCII 큰따옴표를 포함한 제목이 Webhook 페이로드를 깨뜨리지 않음:

```
원본       : 유인원도 긴장하면 서로 끌어안아…"사람처럼 신체접촉 통해 연대감 형성"
title_safe : 유인원도 긴장하면 서로 끌어안아… 사람처럼 신체접촉 통해 연대감 형성
페이로드   : {"content":"[REF] 유인원도 긴장하면 서로 끌어안아… 사람처럼 신체접촉 통해 연대감 형성"}
```

## 8. 구현체 대응표 (한눈에 보기)

| 규격 단계 | Make 구현 | n8n 구현 |
|---|---|---|
| Trigger | ① RSS › Watch RSS feed items | ① RSS Feed Trigger |
| 정규화 | ② Tools › Set multiple variables | ② Code (Run Once for All Items) |
| 스코어링 | ③ Tools › Set multiple variables | ② 동일 노드 내 처리 |
| 분기 | ④ Router + 필터 2개(B=Fallback) | ③ Switch (Fallback Output=REF) |
| CORE 적재 | ⑤ Google Sheets › Add a Row | ④ Google Sheets › Append Row |
| CORE 알림 | ⑥ HTTP › Make a request | ⑤ HTTP Request |
| REF 적재 | ⑦ Google Sheets › Add a Row | ⑥ Google Sheets › Append Row |
| **모듈/노드 수** | **7** | **6** |

모듈 수 차이(7 vs 6)는 구현 실패가 아니라 **추상화 수준의 차이**다. n8n은 Code 노드 1개가 정규화+스코어링을 함께 처리하고, Make는 선언형 수식이므로 변수 참조 단계를 분리해야 한다. 이 차이의 의미는 비교 분석 보고서에서 다룬다.
