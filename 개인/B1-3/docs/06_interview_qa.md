# 항목 2 — 동작 구조 및 설계

## Q1. 두 도구에서 동일성(입력 이벤트 / 핵심 Action / 분기 / 최종 출력)을 맞추기 위해 어떤 설계 기준을 적용했습니까?

**[30초 답변]**
> 도구를 열기 전에 **도구 중립 명세서(TRC-v2)** 를 먼저 작성했습니다. 입력 이벤트·정규화·분기·출력·멱등성 **5개 계약**을 고정하고, Make와 n8n 구현체를 "같은 명세의 서로 다른 실행체"로 취급했습니다. 두 도구의 결과를 같은 스프레드시트의 같은 9열 스키마에 `도구` 열만 달리해 적재했기 때문에, 동일성은 주장이 아니라 **행 단위로 대조 검증**됩니다. 실제로 같은 기사 7건에서 **점수가 7/7 일치**했습니다.

**[확장 답변]** — 5개 계약

| 계약 | 고정한 내용 | 왜 이걸 고정해야 하는가 |
|---|---|---|
| ① 입력 이벤트 | 피드 URL(`rss.etnews.com/06.xml`), "1 item = 1 이벤트", `[포토]` 노이즈 필터, 1일 1회 08:00 KST | 처리 대상이 다르면 점수 분포가 달라져 비교가 무의미해짐 |
| ② 정규화 | HTML 태그·엔티티 제거, 공백 정리, 200자 절단, **Asia/Seoul 고정**, JSON 안전화 | 타임존을 안 고정하면 Make(서버 UTC)와 n8n(기본 America/New_York)의 시각이 어긋남 |
| ③ 분기 | 가중 2단 사전(T1 2점 / T2 1점), **중복 카운트 금지**, θ=2 | 같은 키워드 3회 등장을 3점으로 세면 기사 길이가 점수를 좌우함 |
| ④ 출력 | Sheets 9열 순서, Discord 4행 템플릿 문자열 | 출력이 다르면 "같은 워크플로우"라 할 수 없음 |
| ⑤ 멱등성 | dedup key = `link`, 폴링 상태 저장 책임의 소재 | 이걸 놓치면 n8n 쪽에서 매 실행 전량이 중복 적재됨 |

**방법론적 장치 ①** — 스코어링 로직을 **도구에 넣기 전에 Node.js로 단위 테스트**했습니다(`workflows/_test_scoring.js`). 로직을 도구 밖에서 확정했기 때문에, 두 구현체에서 나타난 차이가 전부 **도구의 차이**로만 남습니다.

**방법론적 장치 ②** — 실행 중에 문제가 생겼습니다. 전자신문 RSS는 실시간 피드이고 두 실행 사이에 4시간 반이 흘러 **입력 집합이 달라졌습니다**(필터 통과 42 vs 49). 집계값으로는 동일성을 증명할 수 없게 된 겁니다.
그래서 **검증 단위를 집계에서 레코드로 내렸습니다.** 같은 `링크`를 가진 행끼리 점수를 대조했고 7/7 일치했습니다. **집계 비교는 우연히 맞을 수 있지만, 레코드 대조는 로직 동일성을 직접 증명합니다.**

**동일성을 위해 의도적으로 포기한 것**: n8n에는 Discord 전용 노드가 있지만 쓰지 않고 HTTP Request를 썼습니다. Make 쪽이 HTTP 모듈이므로 **알림 전송 계층의 추상화 수준을 맞추기 위해서**입니다. 전용 노드가 더 편했겠지만 그 편의가 비교를 오염시킵니다.

**그리고 완전 일치를 주장하지 않습니다** — 불일치 1건을 찾았습니다. `매칭키워드` 표기가 Make는 `출시,확대,`(후행 쉼표), n8n은 `출시,확대` 입니다. Make의 `replace(...; "/,$/"; "")` 가 동작하지 않았고 원인은 미규명입니다. **출력 계약을 '값'까지만 정의하고 '표기'까지 정의하지 않으면 생기는 틈**이었습니다.

## Q2. 워크플로우를 "Trigger → Action → 분기 → 출력" 구조로 단계별 입력/출력을 포함해 설명해 주세요.

**[30초 답변]**
> 전자신문 RSS에 새 기사가 올라오면(**Trigger**) → `[포토]` 사진 캡션을 걸러내고, 제목·요약을 정규화한 뒤 가중 2단 시그널 사전으로 점수를 계산합니다(**Action 1·2**) → 2점 이상이면 CORE, 미만이면 REF로 갈라(**분기**) → CORE는 시트 적재 + Discord 알림, REF는 시트 적재만 합니다(**출력**).

**[확장 답변]** — 각 단계의 입력/출력을 실측값으로

| 단계 | 입력 | 처리 | 출력 (Make 실측) |
|---|---|---|---|
| **Trigger** RSS | 없음 (폴링) | 피드 item 반환 | 50건 |
| **노이즈 필터** | `title` | `[포토]` 포함 시 차단 | 42건 통과 / 8건 차단 |
| **Action 1** 정규화 | `title`·`summary`·`dateCreated`·`url` | 태그·엔티티 제거 → 200자 절단 → KST 변환 → JSON 안전화 | `title_clean`, `published_kst`=`2026-07-29 10:37`, `haystack` |
| **Action 2** 스코어링 | `haystack` | T1 2점 / T2 1점, 고유 개수 집계 | `matched`=`투자,공급,진출`, `score`=`4` |
| **분기** Router / If | `score` | `score >= 2` 판정 | CORE 8 / REF 34 |
| **출력 A** | CORE 레코드 | Sheets `CORE` 9열 적재 → Discord POST | 행 8개 + 알림 8건 |
| **출력 B** | REF 레코드 | Sheets `REF` 9열 적재 | 행 34개 |

**검증**: `8 + 34 = 42` — 필터 통과 건수와 정확히 일치, 유실 0.

**단계 경계를 이렇게 그은 이유**: 정규화와 스코어링을 분리한 것은 Make의 제약(같은 모듈 내 변수 상호 참조 불가) 때문이기도 하지만, 본질적으로 **"데이터를 믿을 수 있게 만드는 일"과 "데이터로 판단하는 일"은 다른 관심사**입니다. 정규화 규칙이 바뀌어도 판단 규칙은 그대로여야 합니다.

**노이즈 필터를 맨 앞에 둔 이유**는 품질과 비용이 동시에 개선되기 때문입니다. Make는 차단된 번들이 하위 모듈 오퍼레이션을 전혀 소모하지 않아 **회당 24 오퍼레이션(15%)이 절감**됐습니다.

## Q3. 조건 분기(Filter/Router)를 어떤 기준으로 설계했습니까?

**[30초 답변]**
> "무엇을 중요하다고 볼 것인가"를 **명시적 규칙으로 외부화**하는 것이 기준이었습니다. 기술경영 관점에서 **되돌릴 수 없는 자원 배분 결정(T1, 2점)** 과 **방향성 발표(T2, 1점)** 를 구분한 가중 2단 사전 12개를 만들고 θ=2로 잡았습니다. 그리고 **분기 구현에서는 Fallback route를 쓰지 않는다**는 규칙을 세웠습니다 — 실측에서 조용한 유실을 겪었기 때문입니다.

**[확장 답변]** — 설계 원칙 4가지

**1. 주제 필터가 아니라 시그널 필터로 설계했다.**
`AI`, `반도체` 같은 고빈도 주제어를 일부러 뺐습니다. 거의 모든 기사에 있어서 분기가 무의미해집니다. 분기의 목적은 "관심 주제 걸러내기"가 아니라 **"행동이 필요한 건 골라내기"** 입니다.

**2. 가중치는 '구속력'에서 나왔다.**
'투자를 집행했다'와 '개발 중이다'는 정보 가치가 다릅니다. 자본이 이미 투입됐거나 법적 권리가 확정된 것(투자·인수·배당·특허·양산·수주)에 2점, 철회 가능한 방향성 발표(개발·출시·공급·진출·제휴·확대)에 1점을 줬습니다. θ=2는 "T1 1개 또는 T2 2개"를 뜻합니다.

**3. 중복 카운트를 금지했다.**
같은 키워드가 3번 나와도 1회입니다. 안 그러면 **기사 길이가 중요도를 결정**하게 됩니다.

**4. ★ Fallback route를 금지했다 — 실측 사고에서 배운 것.**
처음에는 정반대로 생각했습니다. "명시적 조건 2개를 쓰면 둘 다 안 걸리는 아이템이 사라질 수 있으니, Route B는 Fallback으로 두면 도구가 유실 0을 보장해 준다"고요. **논리적으로 그럴듯했고 실측에서 틀렸습니다.**

```
Make  : Router + Fallback route → 42건 중 CORE 8건만 처리, 34건 소실. 오류 없이 "성공"
n8n   : Switch + 규칙 2개      → 49건 중 REF 40건만 처리, CORE 9건 소실. 오류 없이 "성공"
```

두 도구에서 **같은 종류의 사고를 다른 원인으로** 겪었습니다. n8n 쪽 원인은 규칙 1의 우변만 `Expression` 모드였던 것 — UI에서는 두 규칙이 똑같아 보였습니다.

여기서 원칙 3개를 세웠습니다.
- **도구의 암묵적 동작에 데이터 무결성을 맡기지 않는다.**
- **분기 수단은 MECE가 구조로 보장되는 것을 고른다.** n8n에서 최종적으로 **If 노드**를 택한 이유는 출력이 true/false 2개뿐이라 "어디에도 안 걸리는 아이템"이 원리적으로 없기 때문입니다.
- **검증 등식을 반드시 확인한다** — `CORE + REF = 필터 통과 건수`. 이 등식이 두 번 모두 사고를 잡았습니다. 등식이 없었다면 둘 다 "성공"으로 보였을 겁니다.

**5. 비대칭 출력은 의도다.** CORE만 알림을 보냅니다. 알림 채널의 가치는 신호/잡음 비율이고, 실측 CORE 비율이 약 19%이므로 운영 프로파일(5건/일)에서 하루 1건 수준으로 유지됩니다.

# 항목 3 — 핵심 기술 원리 적용

## Q4. Trigger와 Action의 차이를 예시와 함께 설명해 주세요. 왜 Trigger가 "시작점"이고 Action이 "처리"입니까?

**[30초 답변]**
> Trigger는 **"언제 실행할지를 결정하는 유일한 지점"**, Action은 **"주어진 데이터를 변환·전달하는 지점"** 입니다. 결정적 차이는 **호출 방향**과 **상태 보유 여부**입니다. Trigger는 외부 상태를 관찰하고 "어디까지 처리했는지"를 기억하며, Action은 매 호출이 독립적입니다. 그래서 Trigger는 워크플로우당 하나이고 Action은 여럿일 수 있습니다.

**[확장 답변]**

| | Trigger (RSS Watch / Schedule) | Action (Sheets Add a Row / HTTP POST) |
|---|---|---|
| 호출 방향 | 외부 상태를 **관찰** (또는 외부가 나를 깨움) | 외부에 **명령** |
| 입력 | 없음 — 스스로 시각과 상태를 근거로 발화 | 이전 단계의 출력 |
| 상태(state) 보유 | **있음** — 마지막 처리 지점을 기억 | 없음 |
| 개수 | 워크플로우당 **1개** | 제한 없음 |
| 실패의 의미 | 워크플로우 전체가 시작되지 않음 (**조용한 실패**) | 해당 단계만 실패 |
| 재실행 | 개념이 없음 (다음 폴링을 기다림) | 재시도 가능 |

**"Trigger가 상태를 갖는다"가 핵심이고, 이걸 실측으로 확인했습니다.**

n8n에서 `Schedule Trigger + RSS Read` 조합을 썼더니 **매 실행마다 50건 전량이 다시 처리**됩니다. `RSS Read` 는 이름 그대로 **Action**이라 상태가 없고, "무엇이 신규인지 기억하는 책임"이 아무에게도 없기 때문입니다. Make가 상태 저장 트리거에 `Watch` 접두어를 붙여 규약화한 것도 같은 이유입니다 — **`Watch` 는 "내가 기억한다"는 선언**입니다.

**반대 방향의 경계 조건도 겪었습니다.** Make의 `Watch RSS feed items` 는 멱등성을 보장한다고 알려져 있지만, 채점 데이터를 확보하려고 `Choose where to start` 를 3회 리셋했더니 **같은 기사가 시트에 3번 적재**됐습니다. **"도구가 멱등성을 보장한다"는 말은 정확히는 "정상 폴링 경로에서만"이라는 뜻**입니다. 개발 단계와 운영 단계의 보장 범위가 다릅니다.

**프로젝트 2에서는 이 문제를 반대로 풀었습니다.** HTTP 폴링이라 트리거가 아무것도 기억해 주지 않으므로, 상태를 저장하는 대신 **질의 자체를 멱등하게** 만들었습니다 — `bgn_de = end_de = 전일` 이라는 날짜 창으로 고정하면 몇 번을 재실행해도 같은 결과가 나옵니다. **같은 개념(멱등성)을 두 가지 방식(상태 저장 / 무상태 질의)으로 풀어본 것이 두 프로젝트의 학습 가치입니다.**

**한 문장 정리**: Trigger는 *시간과 상태*를 다루고, Action은 *데이터*를 다룹니다.

## Q5. 비교한 도구들의 차이를 "업무 요구사항" 관점으로 연결해 설명해 주세요 (협업/운영/디버깅/확장/비용).

**[30초 답변]**
> 두 도구의 차이는 기능 유무가 아니라 **"어떤 비용을 누가 지불하는가"의 배치 차이**였습니다. Make는 환경·인증·호스팅·가용성 비용을 플랫폼이 지불하고 사용자는 실행량과 데이터 위치를 내줍니다. n8n은 사용자가 그 비용을 지불하고 실행량 한계비용과 데이터 주권을 얻습니다. 그래서 도구 선정은 **업무 요구사항을 비용 항목으로 번역하는 작업**입니다.

**[확장 답변]** — 요구사항 → 비용 항목 → 도구 (전부 실측 근거)

| 업무 요구사항 | 번역된 비용 항목 | 우세 도구 | 정량 근거 |
|---|---|---|---|
| **협업** — 비개발자 인수인계 | 문서화 비용 | **Make** | 캔버스·History가 그대로 문서. n8n Community는 SSO·RBAC이 없어 공유 자체가 제한됨 |
| **운영** — 내가 없어도 돌아야 함 | 가용성 비용 | **Make** | 관리형 24/7. n8n 로컬은 **터미널을 닫으면 정지**, PC 절전 시 트리거 미발화 |
| **디버깅** — 규칙을 반복 개선해야 함 | 시행착오 비용 | **n8n** | 노드 단위 재실행·Pin Data가 무료. Make는 재실행마다 op 소모 (구현 중 427/1,000 소모) |
| **확장** — 처리량 증가 | 한계비용 | **n8n** | Make 135 op/회 → 50건 매일이면 월 4,050으로 무료 한도 4배 초과. n8n은 0 |
| **확장** — 분기 규칙 12개 → 30개 | 유지보수 비용 | **n8n** | 키워드 1개 추가 = Make는 400자 수식 2곳 수정, n8n은 배열에 문자열 1개 |
| **비용** — 월 1,000회 이하 | 총소유비용 | **Make** | 무료 플랜 내 0원. n8n은 상시 구동 인프라 비용 발생 |
| **보안** — 사내·개인정보 | 데이터 주권 비용 | **n8n** | 데이터·자격증명이 자체 인프라를 벗어나지 않음 |
| **첫 구현 속도** | 도입 비용 | **Make** | 30분 vs 90분. 차이의 2/3이 런타임 설치와 자격증명 발급 |

**핵심은 "승패"가 아니라 가중치입니다.** 같은 사람이 만든 두 자동화가 서로 다른 요구사항을 가졌다는 사실이 그 증거입니다 — 프로젝트 1(리서치 큐레이션)은 하루 놓쳐도 다음 날 회복되지만, 프로젝트 2(공시 레이더)는 **가동 중단이 곧 관측 공백**입니다. **요구사항의 실패 비용이 다르면 가중치가 다르고, 가중치가 다르면 도구가 달라집니다.**

**예상하지 못했던 축도 하나 발견했습니다** — **외부 API Rate Limit**. 같은 Discord 알림인데 Make(8건)는 문제없었고 n8n(9건)은 **429 Rate Limited** 가 났습니다. n8n의 병렬성이 더 높기 때문입니다. **성능이 좋은 것이 항상 유리하지는 않다**는 것을 실물로 확인했습니다.

## Q6. 프로젝트 2에서 이 도구를 선택한 이유를 비교 항목 2개 이상과 연결해 설명해 주세요.

**[30초 답변]**
> Make를 선택했고, 비교 항목 **⑧ 호스팅·가동 지속성**, **⑤ 실행 로그·디버깅**, **③ 무료 플랜·과금 모델** 3개가 근거입니다. 이 업무(DART 공시 전략 시그널 레이더)의 실패는 "느림"이 아니라 **"관측 공백"** 이라서 24/7 가동이 곧 요구사항이고, 시그널 사전을 계속 다듬어야 하므로 API 응답 원문과 분류 결과를 함께 보관하는 실행 로그가 개선 데이터가 되며, 활성 시나리오 2개 한도를 P1+P2로 정확히 소진하도록 설계했습니다.

**[확장 답변]**

**근거 ① 항목 ⑧ 가동 지속성 (결정적)**
프로젝트 1 구현 중 n8n을 로컬에서 돌리며 확인했습니다 — **터미널을 닫으면 정지합니다.** 노트북 절전 시에도 트리거가 발화하지 않습니다. 공시 레이더의 가치는 §1.2에서 정의한 대로 **관측 공백 0**에서 나오므로, 실행 주체의 가동률이 곧 요구사항입니다. n8n을 상시화하려면 VPS를 임대해야 하고 그 순간 "무료"가 사라집니다.

**근거 ② 항목 ⑤ 실행 로그 (운영)**
이 워크플로우의 핵심 자산은 시그널 서식명 사전이고, 이 사전은 계속 다듬어야 합니다. Make History는 **HTTP 응답 원문(공시 목록 JSON)과 분류 결과를 함께** 보관하므로 "왜 이 공시가 SIGNAL로 안 잡혔는가"를 원문과 대조해 역추적할 수 있습니다. 실제로 이 로그로 두 가지 실패를 잡았습니다 — 파라미터를 Headers에 넣어 427 B 응답이 온 것, 그리고 `matched` 변수가 100건 전부 빈 값이었던 것입니다. ROUTINE 시트에 쌓인 99행 자체가 사전 개선 백로그가 됩니다.

**근거 ③ 항목 ③ 무료 플랜 (예산)**
Make Free는 활성 시나리오 2개입니다. P1(TRC-v2) + P2(DSR-v1)로 정확히 소진되도록 설계했습니다. 세 번째 자동화가 필요해지는 순간이 n8n 셀프호스팅으로 넘어갈 지점이고, **그 선을 미리 정해 둔 것 자체가 설계**입니다.

**이 업무에서는 n8n이 이기는 축이 무의미해집니다.** 서식명 문자열 매칭 1단계라 Code 노드의 표현력 우위(항목 ⑦)가 발휘될 여지가 작고, 공개 공시 데이터라 데이터 주권 비용도 0입니다.

**감수한 트레이드오프도 말씀드립니다.** 오퍼레이션 과금(검증 실행 1회에 약 202 op), 활성 시나리오 한도 소진, API 키가 Make 클라우드에 저장된다는 점입니다. 마지막 항목은 **DART 키를 고른 것 자체가 완화책**입니다 — 공시 조회 전용이라 개인정보 접근이 없고, 노출되면 재발급에 1분이 걸립니다. 실제로 캡처 중 노출되어 즉시 재발급했습니다.

## Q7. 트리거가 불안정하거나 외부 연동이 자주 실패한다면 모니터링 / 재시도 / 대체 경로를 어떻게 설계하겠습니까?

**[30초 답변]**
> 실패를 **3가지로 분류**해서 각각 다르게 다룹니다. ① **조용한 실패**(트리거가 아예 안 돎, 분기가 데이터를 삼킴) ② **일시적 실패**(429/5xx·타임아웃) ③ **영구적 실패**(401 인증 만료·404). 조용한 실패는 재시도로 잡을 수 없어 **하트비트와 검증 등식**이 필요하고, 일시적 실패는 **지수 백오프 재시도**, 영구적 실패는 즉시 에스컬레이션 + **대체 경로로 데이터를 보존**합니다.

**[확장 답변]**

### ① 모니터링 — 실패 유형별로 감지 방법이 다르다

| 실패 유형 | 감지 방법 | 구현 |
|---|---|---|
| Action 실패 (예외 발생) | 도구의 오류 알림 | Make: 시나리오 설정 → 오류 시 이메일 알림 ON / n8n: Error Trigger 워크플로우 |
| **조용한 실패 — 트리거 미발화** | **하트비트(Dead man's switch)** | 매 실행 종료 시 `_heartbeat` 시트에 타임스탬프 1행. 별도 감시 시나리오가 26시간 이상 갱신이 없으면 경보 |
| **조용한 실패 — 분기 유실** | **검증 등식** | `CORE + REF = 필터 통과 건수`. **이번에 두 도구에서 각각 사고를 잡아낸 실제 장치** |
| 부분 실패 — 결과 품질 이상 | 품질 지표 감시 | CORE 비율이 0% 또는 100%로 3일 연속 고정되면 스코어링 이상 신호 |

**하트비트가 핵심입니다.** 트리거가 안 돌면 실행 기록 자체가 없어서 도구의 오류 알림이 작동하지 않습니다. **"없어야 할 것이 없음"은 감지할 수 없고, "있어야 할 것이 없음"만 감지할 수 있습니다.** 그래서 성공 기록을 남기고 그 부재를 감시합니다.

**그리고 이번 과제에서 배운 것은, 조용한 실패가 트리거만의 문제가 아니라는 겁니다.** Make의 Fallback route 34건, n8n의 Switch 9건 — **둘 다 워크플로우가 "성공"으로 표시된 채 데이터가 사라졌습니다.** 검증 등식이 없었다면 두 번 모두 발견하지 못했을 겁니다.

### ② 재시도 — 재시도해도 되는 실패만 재시도한다

| 오류 | 재시도 | 정책 |
|---|---|---|
| 429 Rate limit | ✅ | 지수 백오프 (2s → 8s → 32s), 최대 3회 |
| 500·502·503, 타임아웃 | ✅ | 동일 |
| 401·403 (인증·권한) | ❌ | 즉시 중단 + 에스컬레이션. 재시도는 부하만 늘림 |
| 400 (페이로드 오류) | ❌ | 코드 결함 |
| 404 | ❌ | 대체 경로로 |

**이번 구현에 실제로 넣은 것**: n8n에서 Discord 429가 발생해 `Batching`(1건/1.5초) + `Retry On Fail`(3회/2초)을 적용했습니다. **재시도만으로는 부족했고, 애초에 몰아치지 않게 하는 Batching이 함께 필요했습니다** — 재시도는 사후 대응이고 Rate 제어는 사전 예방입니다.

**재시도는 반드시 멱등성과 함께 설계해야 합니다.** Sheets 적재 후 Discord가 실패해 전체를 재시도하면 시트에 중복 행이 생깁니다. 그래서 제 워크플로우는 **Sheets 적재 → Discord 알림** 순서입니다. 알림 재시도가 데이터를 오염시키지 않습니다. 순서를 뒤집으면 알림이 두 번 갈 수 있는데, **중복 알림은 중복 데이터보다 복구가 쉽습니다.** 재시도 설계는 "무엇을 두 번 해도 안전한가"를 먼저 정하는 일입니다.

### ③ 대체 경로 — 데이터는 잃지 않는다 (Degrade, don't fail)

```
정상     : RSS → 스코어링 → 분기 → [Sheets + Discord]
1차 대체 : Sheets 실패  → _quarantine 시트에 원본 JSON 적재 → 복구 후 재처리 배치
2차 대체 : Discord 실패 → 이메일로 동일 내용 발송 (채널 이중화)
3차 대체 : 둘 다 실패   → Make Data Store에 큐잉 후 다음 실행에서 재발행
최종     : 피드 자체가 죽음 → 보조 피드로 폴백 + 소스 변경 경보
```

원칙은 **"실패하지 않게 만드는 것"이 아니라 "실패해도 데이터를 잃지 않게 만드는 것"** 입니다. 100% 가용성은 개인 무료 플랜으로 달성할 수 없지만 **유실 0은 달성할 수 있습니다.** 알림은 늦어도 되지만 데이터는 사라지면 복구 불가능합니다 — 이 비대칭성이 우선순위를 정합니다.

### ④ 이번 구현에 이미 들어간 안전장치
- **명시적 조건 2개 + 검증 등식** — Fallback에 의존하지 않고 유실을 *검출*
- **If 노드 채택** — MECE를 구조로 보장
- **Batching + Retry On Fail** — 429 사전 예방 + 사후 복구
- **`title_safe` 사전 생성** — 특수문자로 인한 Discord 400 예방 (사후 대응이 아닌 사전 차단)
- **P2의 날짜 창 설계** — 트리거가 상태를 잃어도 질의가 멱등
- **P2의 리터럴 분류값** — 분기 조건과 기록값이 구조적으로 어긋날 수 없음

## Q8. 조건 분기 규칙이 늘어나거나(2개 → 5개) 처리 로직이 복잡해진다면 워크플로우를 어떻게 구조화·모듈화하겠습니까?

**[30초 답변]**
> 분기를 늘리지 않습니다. **분기 개수를 늘리는 대신 "판정"과 "실행"을 분리**합니다. 지금도 Router가 하는 일은 `score` 하나를 보는 것뿐이고 판정 로직은 그 앞 단계에 있습니다. 규칙이 5개가 되면 판정 단계가 `route` 값 하나를 계산하고 분기는 그 값으로만 갈라집니다. 그리고 **규칙 자체를 Google Sheets 룰 테이블로 외부화**해서 규칙 추가가 워크플로우 수정이 아니라 **행 추가**가 되게 만듭니다.

**[확장 답변]**

### 원칙 1. 판정과 실행의 분리

```
❌ 나쁜 확장:  Router에 조건 5개 → 각 경로에 Action 3개씩 = 15개 모듈, 조건식이 5곳에 흩어짐
✅ 좋은 확장:  [판정 단계] route 값 1개 계산 → 분기는 route로만 → 경로별 Action
```

분기 필터에 복잡한 조건식을 넣으면 **비즈니스 규칙이 도구 UI 안에 갇힙니다.** 테스트도 diff도 안 됩니다. 판정을 한 곳에 모으면 그 부분만 단위 테스트할 수 있습니다 — 이번에 `_test_scoring.js` 로 그렇게 했습니다.

**프로젝트 2에서 이 원칙을 어겼고, 대가를 봤습니다.** P2는 `matched` 변수 계산이 실패해서 Router 필터가 원본 필드(`report_nm`)를 직접 검사하도록 바꿨습니다. 동작은 하지만 **조건이 필터 UI에 8행으로 흩어져 있습니다**(OR 4행 + AND 4행). 서식명 사전을 12개로 늘리면 24행이 됩니다. **이 구조는 확장되지 않습니다** — 그래서 P2의 개선 로드맵 1순위가 룰 테이블 외부화입니다.

### 원칙 2. 규칙의 외부화 (Rule Table)

| rule_id | 범주 | 키워드 | 가중치 | 활성 |
|---|---|---|---|---|
| R01 | 자본 조달 | 유상증자 | 2 | Y |
| R02 | 투자·자산 | 신규시설투자 | 2 | Y |
| R03 | 사업 | 공급계약 | 1 | N |

워크플로우는 시작 시 룰 테이블을 읽어 판정합니다. → **규칙 추가 = 행 추가.** 워크플로우를 안 건드리므로 회귀 위험이 없고, 비개발자도 규칙을 바꿀 수 있고, 시트 자체가 변경 이력이 됩니다.
비용은 룰 조회 오퍼레이션 1회. 규칙이 5개를 넘어가면 즉시 회수됩니다.

### 원칙 3. 서브워크플로우로 계층 분리

```
[Orchestrator]  수집 → 정규화 → 판정 → route별 디스패치
      ├─ [Sub: Notify]   알림 채널 전략 (폴백 포함)
      ├─ [Sub: Archive]  저장 전략
      └─ [Sub: Escalate] 사람 개입 요청
```

**분리 기준은 "변경 주기가 다른 것을 같은 파일에 두지 말라"** 입니다. 알림 채널은 자주 바뀌고 저장 스키마는 거의 안 바뀝니다.
단, Make Free는 활성 시나리오 2개 제한이 있어 서브시나리오 분리 자체가 유료 기능이 됩니다. **이 지점이 무료 노코드의 실질적 천장이고, n8n 셀프호스팅으로 넘어갈 두 번째 이유입니다.**

### 원칙 4. 분기 폭발을 곱셈에서 덧셈으로

조건이 독립적으로 3개(중요도 3단계 × 카테고리 4종 × 채널 2개)면 경로가 24개입니다. Router로 풀 문제가 아닙니다.
→ 판정 단계에서 `{tier, category, channels[]}` 를 계산하고 **디스패치는 매핑 테이블 조회**로 처리합니다. 경로 수가 `3×4×2`에서 `3+4+2`로 떨어집니다.

### 원칙 5. 복잡도 임계선을 미리 정해 둔다

아래 중 **2개 이상**이면 노코드 안에서 버티지 않고 코드로 이전합니다.
- 조건 분기 5개 초과
- 수식 하나가 200자 초과 ← **이번 Make 스코어링 수식이 약 400자였다. 이미 넘었다.**
- 같은 규칙이 2곳 이상에 중복 기술됨 ← **`matched` 와 `score` 에 같은 12키워드가 두 번 적혀 있다.**
- 단위 테스트 없이 배포하기 두려움
- 실행 1회의 모듈 수가 20개 초과

**"언제 도구를 바꿀지"를 미리 정해 두는 것 자체가 설계**입니다. 그 선이 없으면 항상 늦게 옮기게 됩니다. 이번 구현은 이미 2개 항목에 걸렸고, 그래서 다음 확장은 n8n입니다.

## Q9. 노코드 자동화로는 한계가 있는 업무 1가지를 들고, 그 이유와 "코딩 기반 자동화의 확장 아이디어"를 설명해 주세요.

**[30초 답변]**
> **DART 공시 원문(XML/PDF)에서 투자 규모·계약 상대방·조건을 구조화 추출하는 업무**입니다. 프로젝트 2에서 실제로 막힌 지점입니다. 지금 제 워크플로우는 "이런 유형의 공시가 났다"까지만 알려주고 **"얼마짜리인가"는 모릅니다.** 노코드로 불가능한 이유는 3가지 — ① 입력이 **레이아웃 정보를 가진 비정형 문서**라 필드 매핑 패러다임에 안 맞고, ② 서식마다 표 구조가 달라 **정답 없는 반복 개선**이 필요한데 노코드는 단위 테스트가 불가능하고, ③ 추출 결과의 **신뢰도를 정량 평가**할 수단이 없습니다.

**[확장 답변]**

### 왜 이 업무가 노코드의 한계인가

| 한계 | 구체적 이유 |
|---|---|
| **입력 구조** | 공시 원문의 표는 셀 병합·다단·각주가 섞인 2차원 레이아웃이다. 노코드의 "필드 → 필드" 매핑 모델은 1차원 레코드를 전제한다 |
| **반복 개선 불가** | 서식마다 표가 다르므로 수십 건으로 회귀 테스트를 돌려야 한다. 노코드에는 테스트 스위트·CI 개념이 없다. 개선했는데 다른 서식이 깨져도 **알 수 없다** |
| **신뢰도 측정 불가** | "추출 정확도 92%"를 계산하려면 정답셋과 자동 평가 루프가 필요하다. 노코드로 평가 파이프라인을 만드는 것은 본래 목적보다 복잡해진다 |
| **비용 구조 역전** | 공시 1건이 표 5개면 노코드 모듈 실행이 수십~수백 회로 폭발한다. 이미 목록 조회만으로 검증 1회에 202 오퍼레이션을 썼다 |
| **버전 관리 부재** | 파싱 규칙은 계속 바뀐다. 무엇을 왜 바꿨는지 diff로 볼 수 없으면 규칙이 부채가 된다 |
| **조용한 실패** | 이번에 Make 수식이 에러 없이 빈 값을 만드는 것을 두 번 겪었다. 파싱은 실패가 훨씬 미묘하다 |

**일반화하면**: 노코드는 **"입력 스키마가 안정적이고, 규칙이 짧고, 실패가 눈에 보이는"** 업무에서 강합니다. 이 업무는 세 조건을 모두 위반합니다.
반대로 지금의 목록 조회는 세 조건을 모두 만족합니다 — **그래서 노코드로 만든 것이 옳았고, 다음 단계는 아닙니다.**

### 코드 기반 확장 아이디어 — 하이브리드 아키텍처

**핵심 판단: 노코드를 버리는 게 아니라, 노코드를 오케스트레이션 계층으로 두고 판단 로직을 코드로 내린다.**

```
[노코드 계층 — Make]        책임: 이벤트 감지 · 라우팅 · 사람 인터페이스
   Schedule → DART list.json → SIGNAL 판정
        │  HTTP POST (rcept_no)
        ▼
[코드 계층 — Python / FastAPI]   책임: 원문 파싱 · 신뢰도 산출
   1. rcept_no 로 원문 조회, 표 추출 (좌표·병합 정보 유지)
   2. 규칙 기반 1차 파싱 → 금액 / 상대방 / 계약기간 / 자기자본 대비 비율
   3. 실패 셀만 LLM 구조화 추출로 폴백 (비용 최소화 — 전량 아님)
   4. 스키마 검증 + confidence 산출
   5. confidence < 0.8 → needs_review = true
        │  JSON 응답
        ▼
[노코드 계층 — Make]        책임: 결과 분배
   confidence >= 0.8 → Sheets 적재 (금액 포함) + 알림
   confidence <  0.8 → "사람 확인 필요" + 원문 링크
        │
        ▼
[피드백 루프]  사람이 교정한 값을 정답셋에 축적 → 회귀 테스트 케이스로 승격
```

**이 설계의 3가지 판단**

1. **경계를 "판단의 복잡도"로 그었다.** 이벤트 감지·알림·기록은 노코드가 압도적으로 저렴합니다. 파싱과 신뢰도 산출만 코드로 내립니다. 전부 코드로 옮기면 스케줄러·인증·알림 채널을 직접 구현해야 하는데, 이미 잘 풀린 문제를 다시 푸는 낭비입니다.
2. **LLM을 1차 수단이 아니라 폴백으로 뒀다.** 전량 LLM 추출은 비용·지연·비결정성이 모두 나쁩니다. 규칙 기반으로 80%를 처리하고 실패 셀만 보내면 비용이 한 자릿수 퍼센트로 떨어지고, **어디서 규칙이 부족한지가 로그로 남습니다.**
3. **`confidence` 와 `needs_review` 를 1급 출력으로 만들었다.** 자동화의 성숙도는 "얼마나 자동으로 하는가"가 아니라 **"자동으로 하면 안 될 때를 아는가"** 로 측정됩니다. 사람 개입을 예외가 아니라 설계된 경로로 둡니다.

**검증 가능성이 진짜 이득입니다.** 코드로 내리면 `pytest` 로 회귀 테스트를 돌릴 수 있고, 정확도를 숫자로 보고할 수 있고, 사람 교정 데이터가 테스트 케이스로 승격됩니다. 노코드에서는 이 루프가 원리적으로 만들어지지 않습니다.

**이번 과제에서 얻은 것을 한 문장으로**: 노코드는 "코딩을 안 하는 방법"이 아니라 **"어디까지가 코딩이 필요 없는 영역인지 판별하는 훈련"** 이었습니다.

# 예상 추가 질문

## Q10. 왜 Zapier를 쓰지 않았습니까?
> Zapier 무료 플랜은 **월 100 태스크 + 2단계 Zap(트리거 1 + 액션 1)** 만 허용하고 멀티스텝·Filter·Paths가 유료입니다. 이 과제의 필수 요구사항인 "Action 2개 이상 + 조건 분기 1개 이상"을 **무료로는 구조적으로 충족할 수 없습니다.** 14일 트라이얼로는 가능하지만 종료 후 워크플로우가 정지해 재현 검증이 불가능해지고, 과제의 과금 리스크 완화 취지에도 어긋납니다. 그래서 무료로 전 요구사항을 만족하는 Make + n8n을 선택했습니다.

## Q11. 무료 한도를 넘으면 어떻게 합니까?
> 3단계입니다. ① **먼저 예산 내로 설계** — 이번에는 처리 건수와 폴링 주기를 오퍼레이션 예산에서 역산했습니다(P1 운영 월 420). 노이즈 필터가 회당 24 op(15%)를 절감한 것도 같은 맥락입니다. ② **한도 근접 시 구조 최적화** — 폴링을 Webhook 푸시로 바꾸면 실제 이벤트 건수만 소모됩니다. P2는 `page_count` 를 낮추거나 `corp_code` 로 대상을 좁힙니다. ③ **그래도 부족하면 워크로드 이전** — 상시 가동이 필요 없는 P1을 n8n 셀프호스팅으로 옮기면 Make 예산이 통째로 비워집니다. **유료 전환은 세 단계를 다 쓴 뒤의 선택지**입니다.

## Q12. 같은 기사가 두 번 기록되지 않는다는 걸 어떻게 보장합니까?
> 정직하게 말하면 **"도구가 보장한다"는 조건부입니다.** dedup key를 `link` 로 정하고 신규 판정을 Make `Watch RSS feed items` 트리거의 상태 저장에 위임했습니다. 그런데 채점 데이터를 확보하려고 트리거 시작 위치를 3회 리셋했더니 **같은 기사가 3번 적재**됐습니다. 즉 보장은 "정상 폴링 경로에서만" 성립합니다.
> n8n은 `RSS Read` 가 Action이라 상태가 아예 없어 매 실행 전량 재처리됩니다 — 운영에 넣으려면 `Remove Duplicates`(이전 실행 대조)가 필수입니다.
> **프로젝트 2에서는 이 문제를 다르게 풀었습니다** — 상태를 저장하는 대신 `bgn_de = end_de = 전일` 이라는 **날짜 창으로 질의를 멱등하게** 만들고, 시트에 `rcept_no`(공시 접수번호, 전역 유일)를 기록해 중복을 사후 판별 가능하게 했습니다.

## Q13. 이 자동화가 만든 실질적 가치는 무엇입니까?
> 시간 절감은 부수 효과입니다(P2 기준 연 약 17시간). 실질 가치는 셋입니다.
> ① **판단 기준의 명문화** — "무엇이 중요한가"를 가중 사전과 임계값으로 외부화했습니다. 기준이 문서화되면 반박하고 개선할 수 있습니다. 머릿속 기준은 그럴 수 없습니다.
> ② **대상 축소의 정량 확인** — P2 실측에서 하루 공시 100건 중 확인 대상이 1건으로 좁혀졌습니다. **사람이 확인해야 할 대상이 1%가 되면, 매일 확인하는 것이 비로소 가능해집니다.**
> ③ **검증 습관** — `CORE + REF = 입력` 등식 하나가 두 도구에서 각각 사고를 잡아냈습니다. 이건 이 과제가 끝나도 남는 자산입니다.

## Q14. 민감정보는 어떻게 관리했습니까?
> ① Discord Webhook URL과 Google 서비스 계정 Private Key는 **스크린샷에서 마스킹**하고 문서에는 `***MASKED***` 로 표기했습니다. ② 서비스 계정 키 JSON은 제출물에 포함하지 않았고 `.gitignore` 로 커밋을 차단했습니다. ③ 저장소의 n8n JSON에 있는 `YOUR_SPREADSHEET_URL_HERE` / `YOUR_DISCORD_WEBHOOK_URL_HERE` 는 **의도된 자리표시자**입니다 — 실제 값을 공개 저장소에 커밋하는 것 자체가 노출이므로, 실행 증빙은 JSON이 아니라 마스킹된 스크린샷으로 냅니다. ④ 계정 이메일은 일부 가림 처리하고, 브라우저는 전체 화면이 아니라 창 영역만 캡처했습니다.
> **그리고 사고가 한 번 있었습니다.** P2 구현 중 DART 인증키가 캡처 화면에 노출됐고, 발견 즉시 재발급해 무효화했습니다. 이 항목을 숨기지 않는 이유는 — 자격증명 관리의 핵심이 "노출을 0으로 만드는 것"이 아니라 **"노출됐을 때 무효화까지의 시간을 짧게 만드는 것"** 이기 때문입니다. 애초에 DART 키를 고른 것도 그 설계입니다: 공시 조회 전용이라 개인정보 접근이 없고 재발급이 1분입니다.
