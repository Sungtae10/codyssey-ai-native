# 자동화 도구 비교 구현 보고서 — Make vs n8n

**과제** Codyssey B1-3 · 노코드 자동화 기초: 워크플로우 설계 (프로젝트 1)
**워크플로우** TRC-v1 — 기술경영 리서치 큐레이션 파이프라인
**비교 도구** Make (클라우드 관리형) · n8n Community Edition (셀프호스팅)
**작성일** 2026-07-26

---

## 1. 요약 (Executive Summary)

동일한 워크플로우 1개를 Make와 n8n으로 각각 구현하고, **구현 전에 도구 중립 명세서(TRC-v1)를 고정한 뒤 두 구현체를 그 명세의 서로 다른 실행체로 취급**하는 방식으로 비교했다.

결론은 "무엇이 더 좋은 도구인가"가 아니라 **어떤 제약 조건에서 어떤 도구의 총소유비용(TCO)이 낮아지는가**로 정리된다.

| 판단 축 | 우세 도구 | 근거 요약 |
|---|---|---|
| 첫 구현까지의 시간 | **Make** | Google 인증이 사전 검증된 OAuth 앱으로 제공됨. n8n 셀프호스팅은 GCP 프로젝트·서비스 계정 발급이 선행 |
| 24/7 가동 보장 | **Make** | 관리형 클라우드. n8n 셀프호스팅은 호스트 PC 가동에 종속 |
| 실행량 확장 시 한계비용 | **n8n** | 실행 횟수 과금 없음. Make는 오퍼레이션 단위 과금 |
| 복잡 로직 표현력·유지보수 | **n8n** | Code 노드로 로직을 한 곳에 응집. Make는 선언형 수식이 모듈 경계로 분산 |
| 데이터 주권·보안 통제 | **n8n** | 데이터가 자체 인프라를 벗어나지 않음 |
| 비개발자 인수인계 | **Make** | 시나리오 캔버스와 실행 히스토리가 그대로 문서 역할 |

**최종 권고**: 개인·소규모의 상시 가동 자동화는 Make, 처리량이 많거나 로직이 복잡하거나 데이터 반출 제약이 있는 자동화는 n8n. 본 과제의 프로젝트 2(DART 공시 레이더)는 "매일 빠짐없는 자동 수집(관측 공백 0)"이 요구사항이므로 **Make를 선택**했다(→ `05_project2_design.md`).

## 2. 대상 워크플로우

기술경영 관점의 산업 뉴스를 매일 자동 수집해 **전략 시그널 점수**로 등급을 나누고, 핵심 등급만 알림으로 밀어내고 전체를 시트에 축적하는 파이프라인이다.

```
[Trigger] RSS 신규 기사 감지 (전자신문 Section901, 1일 1회 08:00 KST, 최대 5건)
    │
    ▼
[Action 1] 정규화 — HTML 태그·엔티티 제거, 200자 절단, KST 시각 통일, JSON 안전화
    │
    ▼
[Action 2] 스코어링 — 전략 시그널 키워드 12개 매칭 → score (0~12)
    │
    ▼
[조건 분기] score >= 2 ?
    ├── YES → CORE ─► [Action 3] Google Sheets(CORE) 적재 ─► [Action 4] Discord 알림
    └── NO  → REF  ─► [Action 5] Google Sheets(REF) 적재     (알림 없음)
```

**요구사항 충족**: Trigger 1개 / Action 5개(요구 2개 이상) / 조건 분기 1개 / 양 경로 실행 확인 ✅

### 2.1 왜 이 주제인가
단순 알림 전달이 아니라 **판단 기준을 코드로 고정한 큐레이션**을 만들고 싶었다. 뉴스는 매일 오지만 의사결정에 쓰이는 것은 소수이고, "무엇을 중요하다고 볼 것인가"는 사람마다 다르다. 그 기준(시그널 키워드 사전 12개 · 임계값 θ=2)을 명시적으로 문서화하면, 자동화가 단순 노동 절감을 넘어 **판단 기준의 재현 가능성**을 만든다. 이것이 조건 분기를 이 워크플로우의 중심에 둔 이유다.

### 2.2 시그널 키워드 사전 (분기 기준의 근거)

| 범주 | 키워드 | 기술경영 프레임 |
|---|---|---|
| 자본시장 시그널 | 투자, 인수, 합병, 지분, 상장 | 기업 지배구조·자본 배분 변화 |
| 기술자산 시그널 | 특허, 양산, 출시 | 기술의 사업화 단계 이동 |
| 제도·정책 시그널 | 규제 | 외부 제약조건 변화 |
| 사업화 시그널 | 계약, 수주, 협력 | 밸류체인·파트너십 재편 |

'AI', '반도체' 같은 고빈도 주제어를 넣지 않았다. 목적은 주제 필터가 아니라 **의사결정 시그널 필터**이기 때문이다.

## 3. 구현 과정 요약

### 3.1 공통 선행 작업
1. Google Sheets `TRC_Research_Log` 생성, 탭 `CORE` / `REF`, 9열 헤더 통일
2. Discord 채널 `#research-core` + Incoming Webhook 발급
3. **도구 중립 명세서 TRC-v1 작성** (입력 이벤트 / 정규화 / 분기 / 출력 / 멱등성 5개 계약)
4. 스코어링 로직을 Node.js로 단위 테스트 → 임계값 θ 결정 및 분기 양방향 발화 사전 확인

> 4번을 먼저 한 것이 이번 구현의 분기점이었다. 도구 위에서 로직을 시행착오로 맞추면 오퍼레이션을 소모하고 실행 이력이 지저분해진다. **로직을 도구 밖에서 확정한 뒤 도구로 옮기면, 두 도구에서 발생하는 차이가 전부 "도구의 차이"로만 남는다.** 비교 분석의 신뢰도를 만드는 방법이다.

### 3.2 Make 구현 (모듈 7개)

| # | 모듈 | 역할 |
|---|---|---|
| ① | RSS › Watch RSS feed items | Trigger — 신규 기사 감지, 최대 5건 |
| ② | Tools › Set multiple variables | 정규화 (7개 변수) |
| ③ | Tools › Set multiple variables | 스코어링 (`matched`, `score`) |
| ④ | Flow Control › Router | 조건 분기 (Route B = Fallback route) |
| ⑤ | Google Sheets › Add a Row | CORE 적재 |
| ⑥ | HTTP › Make a request | Discord 알림 |
| ⑦ | Google Sheets › Add a Row | REF 적재 |

**구현 중 마주친 3가지 벽**

1. **같은 모듈 내 변수 상호 참조 불가** — `Set multiple variables`에서 정의한 변수는 후속 모듈에서만 참조된다. 그래서 `haystack`(판정 대상 문자열)을 원본 필드로 직접 조립해야 했고, 정규화와 스코어링이 두 모듈로 분리됐다.
2. **문자열 결합에 `+`를 쓸 수 없음** — Make는 `+`를 숫자 덧셈으로 해석할 수 있다. 해결: 한 필드 안에 `{{ }}` 표현식 두 개를 공백으로 띄워 나란히 배치하면 자동 결합된다. Make 특유의 관용구다.
3. **Discord JSON 페이로드 파손** — 언론사 제목은 ASCII 큰따옴표 인용을 자주 쓴다. Raw JSON 본문에 그대로 넣으면 400이 난다. 해결: 정규화 단계에서 `[\x22\x5C\x0A\x0D]`를 제거한 `title_safe`를 별도 생성. 정규식을 16진 이스케이프(`\x22`)로 쓴 것은 **수식 문자열 안에 큰따옴표를 중첩시키지 않기 위한** 선택이다.

### 3.3 n8n 구현 (노드 6개)

| # | 노드 | 역할 |
|---|---|---|
| ① | RSS Feed Trigger | Trigger — 신규 기사 감지 (상태 저장 내장) |
| ② | Code (Run Once for All Items) | 정규화 + 스코어링 통합 |
| ③ | Switch (Fallback Output=REF) | 조건 분기 |
| ④ | Google Sheets › Append Row | CORE 적재 |
| ⑤ | HTTP Request | Discord 알림 |
| ⑥ | Google Sheets › Append Row | REF 적재 |

**구현 중 마주친 3가지 벽**

1. **Google 인증이 워크플로우보다 오래 걸림** — 셀프호스팅에는 사전 검증된 OAuth 앱이 없다. GCP 프로젝트 → Sheets API 활성화 → 서비스 계정 발급 → 키 JSON 다운로드 → **스프레드시트를 서비스 계정 이메일과 공유** 순서를 밟아야 한다. 마지막 공유 단계를 빠뜨려 403이 발생했고, 원인 파악에 시간을 썼다.
2. **트리거 선택이 멱등성을 좌우함** — 처음에 `Schedule Trigger + RSS Read`로 만들었더니 매 실행마다 25건 전량이 재적재됐다. `RSS Read`는 상태를 저장하지 않기 때문이다. `RSS Feed Trigger`로 교체해 Make의 `Watch` 트리거와 의미를 맞췄다.
3. **셀프호스팅의 가동 종속성** — `Active` 전환 후에도 호스트 PC를 절전시키면 트리거가 발화하지 않는다. 아키텍처의 결과이지 버그가 아니며, 프로젝트 2의 도구 선택 근거가 됐다.

## 5. 비교 항목 (8개 — 요구 기준 5개 초과)

### ① UI/UX 및 워크플로우 표현 방식

| | Make | n8n |
|---|---|---|
| 캔버스 | 원형 노드가 좌→우 파이프라인으로 배치. Router 분기가 시각적으로 뚜렷 | 사각 노드 + 명시적 연결선. 분기·병합 관계가 그래프로 드러남 |
| 데이터 흐름 확인 | 모듈 위 버블 숫자로 처리 번들 수 표시 | 커넥션 위 item 수 표시 + 노드별 INPUT/OUTPUT 패널 상시 노출 |
| 표현 지향 | 프로세스 도해에 가까움 — 비개발자에게 설명하기 쉬움 | 데이터 파이프라인 다이어그램에 가까움 — 변환 지점 파악이 쉬움 |

**평가**: Make는 "업무 흐름을 보여주는 데" 강하고, n8n은 "데이터가 어떻게 바뀌는지 보여주는 데" 강하다. 인수인계 문서를 따로 만들 여력이 없다면 Make 캔버스 자체가 문서가 된다.

### ② 설정 난이도 및 첫 구현 소요 시간

| 단계 | Make | n8n |
|---|---|---|
| 도구 준비 | 웹 가입 즉시 사용 (~3분) | `npx n8n` 설치 + 소유자 계정 (~10분) |
| Google 인증 | OAuth 클릭 동의 (~2분) | GCP 프로젝트 → API 활성화 → 서비스 계정 → 키 발급 → 시트 공유 (~25분) |
| 워크플로우 구성 | 모듈 7개 (~25분) | 노드 6개 (~20분) |
| **합계(실측 기준)** | **약 30분** | **약 55분** |

**평가**: 차이의 대부분은 워크플로우가 아니라 **자격증명 획득 비용**이다. 이는 셀프호스팅의 구조적 특성이며 1회성 비용이다. 두 번째 워크플로우부터는 격차가 사라진다.

### ③ 무료 플랜 범위 및 과금 모델 (정량)

| 항목 | Make Free | n8n Community (셀프호스팅) |
|---|---|---|
| 실행량 한도 | **월 1,000 크레딧** | **없음** |
| 과금 단위 | 모듈 1개 × 번들 1개 = 1 오퍼레이션 | 없음 (인프라 비용만) |
| 활성 워크플로우 수 | **2개** | 무제한 |
| 최소 실행 인터벌 | **15분** | 제한 없음 (cron 자유) |
| 데이터 전송 | 512MB/월 | 제한 없음 |
| 연동 앱 수 | 3,000+ | 400+ 노드 + HTTP Request로 임의 API |
| 제외되는 기능 | 무료 플랜에서도 Router·Filter·Webhook 사용 가능 | SSO / 로그 스트리밍 / 외부 시크릿 / Git 버전관리 / 프로젝트·RBAC 등 엔터프라이즈 기능 |

| Discord × CORE 2건 | 2 | 60 |
| **합계** | **18** | **540** |

- **"최대 5건 / 1일 1회"는 취향이 아니라 예산에서 역산한 값이다.** 10건·15분 간격으로 돌리면 월 2,880 오퍼레이션으로 무료 한도를 3배 가까이 초과한다.
- 잔여 460 크레딧을 프로젝트 2에 배정 → 활성 시나리오 2개로 무료 한도를 정확히 소진하는 구성이 된다.
- n8n은 이 계산 자체가 불필요하다. 대신 호스트 자원과 가동 관리가 비용으로 이동한다.

**평가**: **처리량이 늘면 손익분기가 뒤집힌다.** 월 1,000 오퍼레이션 이하의 저빈도 자동화는 Make 무료가 절대적으로 유리하고, 건수가 수천 단위로 늘면 n8n 셀프호스팅의 한계비용 0이 압도한다.

> **참고 — Zapier를 비교 대상에서 제외한 근거**
> Zapier 무료 플랜은 **월 100 태스크 + 2단계 Zap(트리거 1 + 액션 1)만 허용**되고 멀티스텝·Filter·Paths는 유료 기능이다. 본 과제의 필수 요구사항(Action 2개 이상 + 조건 분기 1개 이상)을 **무료 플랜으로는 구조적으로 충족할 수 없다.** 14일 Pro 트라이얼로 가능하지만 트라이얼 종료 후 워크플로우가 정지해 재현 검증이 불가능해진다. 과제의 "과금 리스크 완화 가이드"에 부합하지 않으므로 Make + n8n 조합을 선택했다.

### ④ 인증·연동 방식

| | Make | n8n |
|---|---|---|
| Google 연동 | 플랫폼이 소유한 검증된 OAuth 앱 → 클릭 동의 | 사용자가 GCP에서 직접 발급 (OAuth2 또는 서비스 계정) |
| 자격증명 보관 | Make 클라우드 | 자체 인스턴스 (Community는 인스턴스 소유자·생성자만 접근) |
| Gmail 사용 가능성 | 즉시 가능 | **서비스 계정으로는 불가** (도메인 전체 위임 필요, 개인 Gmail 적용 불가) → OAuth2 필수 |
| 미지원 서비스 대응 | HTTP 모듈 | HTTP Request 노드 + 커스텀 노드 개발 가능 |

**평가**: Make는 "연동 비용을 플랫폼이 대신 지불"하는 모델이다. 이 편의의 대가는 자격증명과 데이터가 제3자 클라우드를 경유한다는 점이다. **개인 Gmail 연동이 필요한 자동화라면 이 제약이 도구 선택을 결정짓는다.**

### ⑤ 실행 로그 및 디버깅

| | Make | n8n |
|---|---|---|
| 로그 위치 | `History` (실행별 레코드) | `Executions` (실행별 레코드) |
| 확인 단위 | 모듈별 입력/출력 번들 JSON | 노드별 INPUT/OUTPUT 테이블·JSON·스키마 3뷰 |
| 부분 재실행 | `Run this module only` | 노드 단위 실행 + **Pin Data**로 입력 고정 |
| 반복 디버깅 비용 | 재실행마다 오퍼레이션 소모 | 무료 |

**평가**: 개발 단계의 실질 차이가 가장 크게 벌어진 항목이다. n8n의 **Pin Data는 트리거 응답을 고정해 동일 입력으로 반복 테스트**를 가능하게 한다. 외부 API가 불안정하거나 재현이 어려운 데이터를 다룰 때 결정적이다. Make는 시행착오 자체가 크레딧을 소모하므로 "설계를 먼저 확정"하는 습관을 강제한다.

### ⑥ 상태 관리 및 멱등성 지원 ★ 이번 비교의 핵심 발견

| | Make | n8n |
|---|---|---|
| 폴링 상태 저장 | `Watch` 접두 트리거에 내장 | `RSS Feed Trigger`에 내장 / `RSS Read`에는 **없음** |
| 잘못 선택했을 때 | — | `Schedule + RSS Read` 조합은 매 실행 전량 재처리 → 중복 적재 |
| 보완 수단 | — | `Remove Duplicates` 노드의 이전 실행 대조 옵션 |

**평가**: 노코드 도구에서 "무엇이 신규인지 기억하는 책임"이 어디에 있는지는 UI에 드러나지 않는다. Make는 트리거 이름의 `Watch` 접두어로 규약화해 실수를 줄이고, n8n은 노드 조합의 자유도가 높은 대신 **상태 관리 책임이 설계자에게 넘어온다.** 자유도의 대가가 정확히 여기서 발생한다.

### ⑦ 로직 표현력 및 유지보수성

| | Make | n8n |
|---|---|---|
| 표현 수단 | 선언형 내장 함수 (`if` `contains` `add` `replace` `formatDate` …) | JavaScript / Python Code 노드 |
| 12개 키워드 매칭 | `if(contains(...))` 12개를 `sum()`으로 합산 — 1줄 수식 약 400자 | 배열 + `for` 루프 — 4줄 |
| 키워드 1개 추가 시 | 2개 변수의 긴 수식을 각각 수정 (누락 위험) | 배열에 문자열 1개 추가 |
| 로직 위치 | 모듈 경계로 분산 | Code 노드 1개에 응집 |
| 버전 관리 | 시나리오 블루프린트 JSON 내보내기 | 워크플로우 JSON + Code 텍스트 diff 가능 |

**구현 중 확인한 Make 함수 라이브러리의 실제 경계** (공식 함수 목록 대조 결과)

| 기대했던 함수 | 실제 | 대응 |
|---|---|---|
| `add(a; b; …)` | **없음** — 개별 숫자 합산은 `sum(a; b; …)` | `sum()`으로 작성 |
| `dateDifference(d1; d2; unit)` | **없음** | 날짜 차이는 `{{round((d1 - d2)/1000/60/60/24)}}` 로 직접 계산, 또는 `addDays()` + Date 연산자로 원값 비교 |
| 같은 모듈 내 변수 상호 참조 | **불가** | 정규화/스코어링 모듈 분리 |
| 문자열 결합 `+` | 숫자 덧셈으로 해석될 수 있음 | 한 필드에 `{{ }}` 표현식을 인접 배치 |

**선언형 노코드의 실질적 학습 비용은 "무엇을 할 수 있는가"가 아니라 "무엇이 없는가"를 알아내는 데 있었다.** 코드 환경에서는 함수가 없으면 즉시 에러가 나지만, 노코드 수식 편집기에서는 잘못된 함수명이 조용히 빈 값을 만들어 분기가 항상 한쪽으로만 흐른다. 이 침묵이 디버깅 비용의 실체다.

**평가**: **분기 규칙이 늘어날 때 유지보수 비용의 증가 기울기가 다르다.** 키워드 12개까지는 Make도 감당되지만, 24개·가중치·다국어로 확장되면 선언형 수식은 사실상 읽을 수 없게 된다. 반대로 Make의 제약은 "복잡한 로직을 노코드 안에 밀어넣지 말라"는 신호로도 기능한다 — 이 신호를 무시한 결과가 유지 불가능한 수식이다.

### ⑧ 호스팅·가동 지속성 및 운영 부담

| | Make | n8n Community (셀프호스팅) |
|---|---|---|
| 가동 주체 | Make 클라우드 (24/7) | 사용자 호스트 |
| PC 종료·절전 시 | 정상 실행 | **트리거 미발화** |
| 가용성 확보 방법 | 불필요 | VPS/NAS 상시 구동 또는 Docker + 재시작 정책 |
| 장애 대응 | 플랫폼 책임 | 사용자 책임 (백업·업데이트·복구 포함) |
| 상시 운영 비용 | 무료 플랜 내 0원 | VPS 기준 월 수천 원 이상 (또는 기존 장비 전력) |

**평가**: 노코드 자동화의 가치는 "내가 없을 때도 돌아간다"에 있다. **로컬 셀프호스팅은 이 전제를 부분적으로 깨뜨린다.** n8n을 선택한다면 상시 구동 인프라를 함께 설계해야 하고, 그 순간 "무료"는 사라진다. 이 항목이 프로젝트 2에서 Make를 고른 1순위 근거다.

## 6. 장단점 정리

### Make

**장점**
1. 첫 구현까지 30분 — 자격증명 획득 비용을 플랫폼이 흡수
2. 무료 플랜에서 Router·Filter·Webhook을 모두 제공 (Zapier 무료는 불가)
3. 24/7 관리형 가동 — 개인 장비 상태와 무관
4. 시각적 캔버스와 실행 히스토리가 그대로 인수인계 문서가 됨
5. 오퍼레이션 과금이 "설계를 먼저 확정하는" 규율을 강제

**단점**
1. 월 1,000 오퍼레이션 / 활성 시나리오 2개 — 확장 시 즉시 유료 전환 압력
2. 임의 코드 실행 불가 → 복잡 로직이 긴 수식으로 파편화
3. 같은 모듈 내 변수 상호 참조 불가 등 문법적 제약이 모듈 수를 늘림
4. 디버깅 시행착오가 크레딧을 소모
5. 자격증명·데이터가 제3자 클라우드를 경유

### n8n Community (셀프호스팅)

**장점**
1. 실행 횟수 한계비용 0 — 처리량 확장에 강함
2. Code 노드로 로직을 한 곳에 응집, Git diff 가능
3. Pin Data로 입력을 고정한 반복 디버깅이 무료
4. 데이터·자격증명이 자체 인프라를 벗어나지 않음
5. 노드 조합 자유도가 높고 커스텀 노드 개발 가능

**단점**
1. 자격증명 획득이 진입장벽 (GCP 프로젝트·서비스 계정 발급 필수)
2. 로컬 구동 시 24/7 가동 미보장 → 상시화하려면 인프라 비용 발생
3. 상태 관리·멱등성 책임이 설계자에게 있음 (노드 선택 실수 시 중복 적재)
4. 백업·업데이트·복구가 사용자 책임
5. 서비스 계정으로 Gmail 사용 불가 등 인증 제약을 스스로 파악해야 함
6. Community Edition은 SSO·RBAC·Git 버전관리 등 협업 기능이 제외됨

## 8. 결론

두 도구의 차이는 기능표의 유무가 아니라 **"어떤 비용을 누가 지불하는가"의 배치 차이**였다.

Make는 인증·호스팅·가용성 비용을 플랫폼이 지불하고, 사용자는 실행량과 데이터 위치를 내준다.
n8n은 사용자가 인증·호스팅·상태관리 비용을 지불하고, 실행량 한계비용과 데이터 주권을 얻는다.

따라서 도구 선정은 기능 비교표가 아니라 **업무 요구사항을 비용 항목으로 번역하는 작업**이다. 이번 워크플로우에서 그 번역은 이렇게 됐다.

- "매일 아침 자동으로 돌아야 한다" → **가동 지속성 비용** → Make 우위
- "하루 5건, 월 150건 수준" → **실행량 비용 미미** → Make 우위
- "판단 기준(키워드·임계값)을 계속 다듬을 것이다" → **로직 유지보수 비용** → n8n 우위
- "공개 뉴스 데이터만 다룬다" → **데이터 주권 비용 0** → 판단에 영향 없음

3승 1패가 아니라, **네 축의 가중치가 상황마다 바뀐다**는 것이 이 비교의 결론이다. 프로젝트 2에서는 첫 두 축의 가중치가 압도적이었으므로 Make를 선택했다.
