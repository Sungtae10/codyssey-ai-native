# TRC-v2 도구 중립 워크플로우 명세서
**Tool-Neutral Workflow Specification — TechMgmt Research Curator**

| 항목 | 내용 |
|---|---|
| 명세 ID | **TRC-v2** (v1을 Make 실측으로 개정) |
| 목적 | 기술경영 관점의 산업 뉴스를 자동 수집 → 전략 시그널 점수화 → 중요도 분기 → 아카이빙/알림 |
| 적용 대상 | 프로젝트 1 (Make 구현체 · n8n 구현체) |
| 작성 근거 | 평가 항목 2 "두 도구에서 동일성(입력 이벤트/핵심 Action/분기/최종 출력)을 맞추기 위해 어떤 설계 기준을 적용했는가" |
| 구현·측정일 | 2026-07-30 |
| 개정 이력 | v1 → v2 (§8 개정 로그) |

> **이 문서의 존재 이유**
> "같은 워크플로우를 두 도구로 만들었다"는 주장은 검증 가능해야 한다. 도구별 UI를 먼저 만들고 나중에 비교하면 "우연히 비슷한 것"이 되고, 심사자가 "어디까지 같은 건가"를 물었을 때 답이 흔들린다.
> 그래서 **구현 전에 도구와 무관한 계약 5개를 고정**하고, 두 구현체를 이 계약의 서로 다른 실행체로 취급했다. 계약이 같으면 동일 워크플로우이고, 계약을 지키는 방식의 차이가 곧 비교 분석 결과가 된다.
>
> **그리고 v1은 실측에서 틀렸다.** 그 사실과 수정 과정을 §8에 남긴다 — 명세서는 처음부터 옳았음을 주장하는 문서가 아니라, **무엇을 근거로 바뀌었는지 추적 가능하게 만드는 문서**다.

## 1. 계약 ① 입력 이벤트 계약 (Input Event Contract)

| 항목 | 규격 |
|---|---|
| 소스 | 전자신문 **전자 섹션** RSS — `https://rss.etnews.com/06.xml` |
| 형식 | RSS 2.0, `<item>` 50건 (실측 2026-07-30) |
| 이벤트 1건의 정의 | 피드의 `<item>` 1개 = 1 bundle / 1 item |
| **노이즈 필터** | 제목에 `[포토]` 포함 시 **처리 대상에서 제외** |
| 실측 처리 대상 | Make **42건** (50 − 8) / n8n **49건** (50 − 1) |
| 폴링 주기 | 1일 1회 **08:00 KST** |
| 운영 시 처리 건수 | 5건 (오퍼레이션 예산 — §6) |
| 검증 시 처리 건수 | 50건 (분기 양쪽 증빙 확보용) |
| 필수 입력 필드 | 제목, 링크, 요약, 발행일시 |

### 1.1 노이즈 필터를 계약에 넣은 이유

`[포토]` 기사는 **사진 캡션**이라 본문 정보가 없고, 실측에서 같은 내용이 3건 중복 등장했다. 스코어링 대상에 넣으면 점수 분포를 왜곡한다.
필터를 **트리거 직후**에 배치한 것은 비용 때문이기도 하다 — Make는 트리거가 몇 건을 반환해도 1 오퍼레이션이고, 차단된 번들은 하위 모듈 오퍼레이션을 전혀 소모하지 않는다. **입력 품질 관리를 파이프라인 최상단에 두면 품질과 비용이 동시에 개선된다.**

### 1.2 필드명 매핑 (도구별로 다름 — 실측 확정)

| 규격 필드 | **Make** (RSS: Watch RSS feed items) | **n8n** (RSS Read, `rss-parser`) |
|---|---|---|
| 제목 | `title` | `title` |
| 링크 | **`url`** | **`link`** |
| 요약 | **`summary`** | **`contentSnippet`** (fallback `content`) |
| 발행일시 | **`dateCreated`** | **`isoDate`** (fallback `pubDate`) |

> **같은 RSS를 읽어도 커넥터가 부여하는 키 이름이 다르다.** 이 명세서에 매핑 표가 필요한 이유가 바로 이것이다.
> Make 실측 확정 필드: `id`, `title`, `description`, `summary`, `url`, `dateCreated`, `dateUpdated`, `comments`, `author`, `image`, `categories`, `source`, `enclosures`, `rssFields`, `date`

## 2. 계약 ② 정규화 계약 (Normalization Contract)

| # | 규칙 | 정규식 / 처리 | 이유 |
|---|---|---|---|
| N1 | HTML 태그 제거 | `<[^>]*>` → 공백 | etnews `description`이 CDATA + 태그 포함 |
| N2 | HTML 엔티티 제거 | `&[a-zA-Z#0-9]+;` → 공백 | `&nbsp;` `&quot;` 등이 점수 계산을 오염 |
| N3 | 연속 공백 정리 | `\s+` → 공백 1개, 앞뒤 trim | N1·N2가 남긴 공백 흡수 |
| N4 | 요약 길이 제한 | 앞 **200자** | 셀 가독성 + 점수 계산 대상 범위 고정 |
| N5 | JSON 안전화 (`title_safe`) | `["\\\r\n]` → 공백 | Discord Webhook 페이로드가 JSON이므로 제목의 ASCII 큰따옴표가 페이로드를 깨뜨림 |
| N6 | 시각 표기 | `YYYY-MM-DD HH:mm`, **Asia/Seoul 고정** | RSS `pubDate`는 `+0900`, Make 서버는 UTC, n8n 인스턴스 기본은 America/New_York → 통일 없으면 두 시트 값이 어긋남 |
| N7 | 빈 값 처리 | 요약 없으면 빈 문자열, 점수는 제목만으로 | null 전파로 인한 분기 오판 방지 |

### 2.1 표준 출력 레코드 (양 도구 공통)

| 키 | 타입 | 실측 예 |
|---|---|---|
| `collected_at` | string | `2026-07-30 12:52` |
| `tool` | string | `Make` \| `n8n` |
| `tier` | string | `CORE` \| `REF` |
| `score` | number | `4` |
| `matched_keywords` | string | `투자,공급,진출` |
| `title` | string | `韓-브라질, 경제 협력 체계 구축…` |
| `title_safe` | string | N5 적용본 (알림 페이로드 전용) |
| `summary` | string | 200자 이내 |
| `published_at` | string | `2026-07-29 10:37` |
| `link` | string | `https://www.etnews.com/20260729000145` |

## 3. 계약 ③ 분기 계약 (Branch Contract)

### 3.1 가중 2단 시그널 사전 (실측으로 재설계)

기술경영에서 기업의 발표는 **구속력이 다르다.** '투자를 집행했다'와 '개발 중이다'는 정보 가치가 같지 않다. 그래서 **되돌릴 수 없는 자원 배분 결정에 2점, 방향성 발표에 1점**을 부여했다.

| 등급 | 키워드 (6개씩) | 판단 기준 |
|---|---|---|
| **T1 (2점)** | 투자, 인수, 배당, 특허, 양산, 수주 | **비가역적 결정** — 자본이 이미 투입됐거나 법적 권리가 확정됨 |
| **T2 (1점)** | 개발, 출시, 공급, 진출, 제휴, 확대 | **방향성 발표** — 의도는 드러나지만 철회 가능 |

**제외한 어휘와 이유**
- `AI`, `반도체` 등 고빈도 주제어 → 거의 모든 기사에 등장해 분기가 무의미해짐
- 유상증자·합병·지분·상장·규제·계약 (v1 사전) → **공시/증권 어휘라 산업 뉴스 코퍼스에 거의 없음** (실측 0건, §8)

### 3.2 판정 규칙

```
haystack = lower( title(N1~N3) + " " + summary(N1~N4) )
score    = (T1 매칭 고유 개수 × 2) + (T2 매칭 고유 개수 × 1)      # 0 ~ 18
θ (임계값) = 2

tier = score >= 2 ? "CORE" : "REF"
```

- **중복 카운트 금지**: 같은 키워드가 3번 나와도 1회. 기사 길이가 점수를 좌우하지 않게 하기 위함.
- **θ=2의 의미**: "T1 1개" 또는 "T2 2개". 단일 범용어 1개로는 CORE가 되지 않는다.
- **실측 결과**: Make 42건 중 CORE 8건(19%) / n8n 49건 중 CORE 9건(18%) — 사전 튜닝 시 예측한 20%와 일치.

### 3.3 분기 구현 규칙 ★ 실측으로 확정된 금지사항

```
Route A (CORE) :  명시적 조건  score >= 2
Route B (REF)  :  명시적 조건  score <  2

❌ 금지: Fallback route / Fallback Output 에 데이터 무결성을 의존하는 것
❌ 금지: 규칙 우변의 입력 모드(Fixed/Expression)를 규칙마다 다르게 두는 것
```

**금지 근거 ① (Make 실측):** Route B를 `Fallback route`로 설정했을 때 **42건 중 CORE 8건만 처리되고 34건이 어느 경로에도 기록되지 않았다.** 오류가 아니라 **성공으로 표시**됐다 — 조용한 유실이었다. 명시적 조건(`score < 2`)으로 교체하니 34건이 정상 흘렀다.

**금지 근거 ② (n8n 실측):** Switch 노드의 규칙 1 우변만 `Expression` 모드였고 규칙 2는 `Fixed`였다. **49건 중 REF 40건만 처리되고 CORE 9건이 소실**됐으며 역시 "Workflow executed successfully"로 표시됐다. **If 노드로 교체**해 출력이 true/false 2개로 강제되게 만들어 해결했다 — MECE를 선언이 아니라 **구조**로 보장한 것이다.

**여기서 도출한 원칙**: 도구의 암묵적 동작에 데이터 무결성을 맡기지 말고, **조건을 명시적으로 선언하고 건수를 합산 검증**한다.

### 3.4 필수 검증 등식

```
CORE 건수 + REF 건수 = 노이즈 필터 통과 건수

Make :  8 + 34 = 42   ✅ 유실 0
n8n  :  9 + 40 = 49   ✅ 유실 0
```

이 등식이 성립하지 않으면 유실이 발생한 것이다. **이 등식 하나가 두 도구에서 각각 사고를 잡아냈다.**

## 4. 계약 ④ 출력 계약 (Output Contract)

### 4.1 Google Sheets (공동 저장소)

스프레드시트 **1개**(`TRC_Research_Log`)를 두 도구가 공유하고, 시트 탭 2개(`CORE`, `REF`)를 쓴다. `도구` 열로 구현체를 구분한다.
→ **같은 스키마에 두 도구의 결과가 나란히 쌓이는 것 자체가 "동일 워크플로우" 증빙**이 된다.

| 열 | A | B | C | D | E | F | G | H | I |
|---|---|---|---|---|---|---|---|---|---|
| 헤더 | 수집시각 | 도구 | 분류 | 점수 | 매칭키워드 | 제목 | 요약 | 발행일 | 링크 |

실측 적재량 — `CORE` 탭 Make 8행 + n8n 9행 / `REF` 탭 Make 34행 + n8n 40행.

### 4.2 Discord 알림 (CORE 전용)

고정 템플릿 — 양 도구가 같은 문자열을 만들어야 한다.

```
[CORE] {title_safe}
· 점수 {score} / 시그널 {matched_keywords}
· 발행 {published_at} · 수집 {tool}
{link}
```

- **REF는 알림 없음.** 의도적 설계다. 알림 채널의 가치는 신호/잡음 비율이므로, 참고 등급까지 알리면 채널이 무력화된다. 실측 비율이 CORE 약 19%이므로 운영 프로파일(5건/일)에서 하루 1건 수준으로 유지된다.
- **JSON 직렬화는 도구에 위임한다** — Make는 `JSON › Data structure`, n8n은 `Using Fields Below`. 둘 다 예약문자를 자동 이스케이프한다. 그럼에도 N5(`title_safe`)를 적용하는 것은 **두 도구의 알림 본문이 바이트 단위로 같아야** 하기 때문이다.

## 5. 계약 ⑤ 멱등성 계약 (Idempotency Contract)

| 항목 | 규격 |
|---|---|
| 중복 판정 키 | `link` |
| Make | `Watch RSS feed items` 트리거가 마지막 처리 지점을 저장 → 도구 레벨 보장 |
| n8n | `Schedule + RSS Read`는 **상태 없음** → 매 실행 전량 재적재. 운영 시 `Remove Duplicates`(이전 실행 대조) 필수 |
| 검증 | 시트 `링크` 열 중복 여부 |

### 5.1 실측으로 확인된 경계 조건

**상태 저장 트리거의 멱등성은 "트리거 위치를 건드리지 않는 한"에서만 성립한다.**
채점용 데이터를 확보하려고 Make에서 `Choose where to start → All feed items`로 위치를 3회 리셋했더니 **같은 기사가 시트에 3번 적재**됐다. 도구가 멱등성을 보장한다는 말은 정확히는 "정상 폴링 경로에서만"이라는 뜻이다.

→ **개발 단계와 운영 단계의 멱등성 보장 범위가 다르다**는 것이 이 계약의 실측 결론이다.

### 5.2 도구 차이가 만드는 설계 부담

n8n에서 `Schedule + RSS Read`를 택한 것은 채점 요구사항(분기 양쪽 증빙) 때문이며, 그 대가로 **멱등성 책임이 설계자에게 넘어온다.** Make는 트리거 이름의 `Watch` 접두어로 "내가 기억한다"를 규약화해 이 실수를 줄인다. → 비교 항목 ⑥

## 6. 오퍼레이션 예산 (실측 확정)

### 6.1 검증 실행 실측 (Make, 50건 처리)

| 구성 | 오퍼레이션 |
|---|---|
| RSS 트리거 (반환 건수 무관) | **1** |
| 01_정규화 × 42 | 42 |
| 02_스코어링 × 42 | 42 |
| Sheets(CORE) × 8 | 8 |
| HTTP Discord × 8 | 8 |
| Sheets(REF) × 34 | 34 |
| **합계** | **135** |

**Make History 실측값: `Operations: 135` / `Duration: 18 seconds` / `Data size: 190.5 KB`** — 계산과 정확히 일치.

> 노이즈 필터로 차단된 8건은 하위 모듈 오퍼레이션을 소모하지 않았다. 필터 없이 50건을 처리했다면 약 159 오퍼레이션이었을 것이다 → **필터가 회당 24 오퍼레이션(15%)을 절감**했다.

### 6.2 운영 프로파일

| 프로파일 | 처리 건수 | 회당 | 월(30일) |
|---|---|---|---|
| 검증용 (1회성) | 50 | 135 | — |
| **운영용** | **5** | 약 14 | 약 **420** |
| 참고: 50건 매일 | 50 | 135 | 4,050 ❌ 한도 초과 4배 |

- Make Free 한도: **월 1,000 크레딧 / 활성 시나리오 2개 / 최소 인터벌 15분**
- 실측 사용량(2026-07-30 기준): **427 / 1,000 (43%)** — 구현·검증 과정에서 소모
- **"5건 / 1일 1회"는 취향이 아니라 예산에서 역산한 값이다.**
- n8n Community(셀프호스팅)는 실행 과금이 없어 이 계산 자체가 불필요하다. 대신 호스트 자원과 가동 관리가 비용으로 이동한다. → 비교 항목 ③

## 7. 구현체 대응표 (실측 확정)

| 규격 단계 | Make (모듈 번호 실측) | n8n (노드 순서 실측) |
|---|---|---|
| Trigger | ② RSS › Watch RSS feed items | ① Schedule Trigger + ② RSS Read |
| 노이즈 필터 | 모듈 ②→③ 사이 Filter `본문기사만` | ③ Filter 노드 |
| 정규화 | ③ Tools › Set multiple variables (변수 7개) | ④ Code (Run Once for All Items) |
| 스코어링 | ⑥ Tools › Set multiple variables (변수 2개) | ④ 동일 노드 내 처리 |
| 분기 | ⑩ Router + 명시적 조건 2개 | ⑤ **If** (`score >= 2`) |
| CORE 적재 | ⑪ Google Sheets › Add a Row | ⑥ Google Sheets › Append Row |
| CORE 알림 | ⑬ HTTP › Make a request (Data structure) | ⑦ HTTP Request (Using Fields Below + Batching) |
| REF 적재 | ⑫ Google Sheets › Add a Row | ⑧ Google Sheets › Append Row |
| **구성 요소 수** | **모듈 7 + 필터 2** | **노드 8** |

모듈/노드 수 차이는 구현 실패가 아니라 **추상화 수준의 차이**다.
- n8n은 Code 노드 1개가 정규화·스코어링·tier 판정을 함께 처리한다.
- Make는 선언형 수식이고 **같은 모듈 내 변수 상호 참조가 불가**하므로 단계를 분리해야 한다.
- 반대로 Make는 트리거 1개가 폴링·상태저장을 겸하는데, n8n은 Schedule + RSS Read 2개 노드가 필요하다.

## 8. 개정 로그 — v1이 실측에서 틀린 이유

이 절은 감점 요소가 아니라 **가장 중요한 학습 기록**이다.

| # | v1 설계 | 실측 결과 | v2 수정 |
|---|---|---|---|
| 1 | 소스 `Section901.xml` (전체기사) | 반환된 5건이 연예(키오프 컴백)·사회(랜섬웨어) — 전략 시그널 어휘 **0건** | **`06.xml`(전자 섹션)** 으로 교체 |

| 5 | Make 함수 `add()` | Make에 `add()` 없음 | **`sum()`** |

### 9.4 동일성 검증 — 검증 단위를 집계값에서 레코드로 내린 이유

전자신문 RSS는 실시간 피드이고 두 실행 사이에 약 4시간 30분이 흘렀다. `[포토]` 기사가 피드에서 밀려나고 새 기사가 유입되어 **두 도구가 동일 입력 집합을 받지 못했다**(필터 통과 42 vs 49).

집계값이 다르다는 이유로 "동일하지 않다"고 결론 내리는 것은 틀렸다 — 입력이 다르면 출력이 다른 것이 오히려 정상이다. 그래서 **동일성 검증의 단위를 집계에서 레코드로 내렸다.** 같은 `링크`를 가진 행끼리 대조한다.

### 9.5 발견된 불일치 1건 (정직하게 기록)

| 항목 | Make | n8n |
|---|---|---|
| `매칭키워드` 표기 | `출시,확대,` ← **후행 쉼표 있음** | `출시,확대` ← 없음 |

Make에 넣은 `replace(6.matched; "/,$/"; "")` 가 동작하지 않았다. **점수와 키워드 구성은 동일하지만 문자열 표기가 다르다.**

> **교훈**: 출력 계약을 **'값'까지만 정의하고 '표기'까지 정의하지 않으면** 이런 틈이 생긴다. n8n은 `Array.join(',')` 이라 후행 구분자가 원리적으로 생기지 않지만, Make는 조건부 문자열 연결이라 후처리가 필요했고 그 후처리가 실패했다.
> **완전 일치를 주장하는 것보다, 불일치 1건을 찾아 원인을 설명하는 것이 검증의 증거다.**
