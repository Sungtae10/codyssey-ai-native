# 항목 2 — 동작 구조 및 설계

## Q1. 두 도구에서 동일성(입력 이벤트 / 핵심 Action / 분기 / 최종 출력)을 맞추기 위해 어떤 설계 기준을 적용했습니까?

**[30초 답변]**
> 도구를 열기 전에 **도구 중립 명세서(TRC-v1)** 를 먼저 작성했습니다. 입력 이벤트·정규화·분기·출력·멱등성 **5개 계약**을 문자 단위로 고정하고, Make와 n8n 구현체를 "같은 명세의 서로 다른 실행체"로 취급했습니다. 두 도구의 결과를 같은 스프레드시트의 같은 9열 스키마에 `도구` 열만 달리해 적재했기 때문에, 동일성은 주장이 아니라 **행 단위로 대조 검증**됩니다.

**[확장 답변]** — 5개 계약을 순서대로

| 계약 | 고정한 내용 | 왜 이걸 고정해야 하는가 |
|---|---|---|
| ① 입력 이벤트 | 피드 URL, "1 item = 1 이벤트", 최대 5건, 1일 1회 08:00 KST | 처리 건수가 다르면 점수 분포가 달라져 비교가 무의미해짐 |
| ② 정규화 | HTML 태그 `<[^>]*>` 제거, 엔티티 제거, 공백 정리, 200자 절단, **Asia/Seoul 고정**, JSON 안전화 | 타임존을 안 고정하면 Make(서버 UTC)와 n8n(로컬)의 시각이 9시간 어긋남 |
| ③ 분기 | 키워드 12개 사전, **중복 카운트 금지**, 임계값 θ=2 | 같은 키워드 3회 등장을 3점으로 세면 기사 길이가 점수를 좌우함 |
| ④ 출력 | Sheets 9열 순서, Discord 4행 템플릿 문자열 | 출력이 다르면 "같은 워크플로우"라 할 수 없음 |
| ⑤ 멱등성 | dedup key = `link`, 폴링 상태를 트리거에 위임 | 이걸 놓치면 n8n 쪽에서 매일 25건이 중복 적재됨 |

**여기서 만든 방법론적 장치 하나**: 스코어링 로직을 **도구에 넣기 전에 Node.js로 단위 테스트**했습니다(`_test_scoring.js`, 픽스처 5건 → CORE 2 / REF 3). 로직을 도구 밖에서 확정했기 때문에, 두 구현체에서 나타난 차이가 전부 **도구의 차이**로만 남습니다. 이것이 비교 분석의 신뢰도를 만든 결정적 선택이었습니다.

**동일성을 위해 의도적으로 포기한 것도 있습니다.** n8n에는 Discord 전용 노드가 있지만 쓰지 않고 HTTP Request를 썼습니다. Make 쪽이 HTTP 모듈이므로 **알림 전송 계층의 추상화 수준을 맞추기 위해서**입니다. 전용 노드를 쓰면 더 편했겠지만, 그 편의가 비교를 오염시킵니다.

## Q2. 워크플로우를 "Trigger → Action → 분기 → 출력" 구조로 단계별 입력/출력을 포함해 설명해 주세요.

**[30초 답변]**
> 전자신문 RSS에 새 기사가 올라오면(**Trigger**) → 제목·요약을 정규화하고 전략 시그널 키워드 12개를 매칭해 0~12점을 계산합니다(**Action 1·2**) → 2점 이상이면 CORE, 미만이면 REF로 갈라(**분기**) → CORE는 시트 적재 + Discord 알림, REF는 시트 적재만 합니다(**출력**).

**[확장 답변]** — 각 단계의 입력/출력을 값으로

| 단계 | 입력 | 처리 | 출력 (실측 예) |
|---|---|---|---|
| **Trigger** RSS | 없음 (폴링) | 직전 처리 지점 이후 신규 item 최대 5건 | `title`, `link`, `pubDate`, `summary` |
| **Action 1** 정규화 | 위 4개 필드 | 태그·엔티티 제거 → 공백 정리 → 200자 절단 → KST 변환 → JSON 안전화 | `title`=`정의선·젠슨 황, 한달만에 재회…`, `published_at`=`2026-07-25 19:00`, `haystack`=소문자 결합 문자열 |
| **Action 2** 스코어링 | `haystack` | 12개 키워드 포함 여부 검사, 고유 개수 집계 | `matched_keywords`=`양산,계약,협력`, `score`=`3` |
| **분기** Router/Switch | `score` | `score >= 2` 판정 | CORE 2건 / REF 3건 |
| **출력 A** | CORE 레코드 | Sheets `CORE` 탭 9열 적재 → Discord POST | 행 추가 + HTTP 204 |
| **출력 B** | REF 레코드 | Sheets `REF` 탭 9열 적재 | 행 추가 |

**단계 경계를 이렇게 그은 이유**: 정규화와 스코어링을 분리한 것은 Make의 제약(같은 모듈 내 변수 상호 참조 불가) 때문이기도 하지만, 본질적으로 **"데이터를 믿을 수 있게 만드는 일"과 "데이터로 판단하는 일"은 다른 관심사**입니다. 정규화 규칙이 바뀌어도 판단 규칙은 그대로여야 하고, 그 반대도 그렇습니다.

## Q3. 조건 분기(Filter/Router)를 어떤 기준으로 설계했습니까?

**[30초 답변]**
> "무엇을 중요하다고 볼 것인가"를 **명시적 규칙으로 외부화**하는 것이 기준이었습니다. 기술경영 관점의 전략 시그널 키워드 12개를 4개 범주(자본시장·기술자산·제도정책·사업화)로 선별하고, 고유 매칭 개수 2개 이상을 CORE로 정했습니다. 임계값 2는 실측 표본으로 결정했습니다 — θ=1이면 '협력' 같은 범용어 하나로 CORE가 과다해지고, θ=3이면 CORE가 0건이 되는 구간이 생겼습니다.

**[확장 답변]** — 설계 원칙 4가지

1. **주제 필터가 아니라 시그널 필터로 설계했다.** 'AI', '반도체' 같은 고빈도 주제어를 일부러 넣지 않았습니다. 그 단어들은 거의 모든 기사에 있어서 분기가 무의미해집니다. 반면 '인수', '특허', '수주'는 **의사결정 상황의 변화**를 가리킵니다. 분기의 목적은 "관심 주제 걸러내기"가 아니라 "행동이 필요한 건 골라내기"입니다.
2. **중복 카운트를 금지했다.** 같은 키워드가 3번 나와도 1점입니다. 안 그러면 긴 기사가 자동으로 높은 점수를 받아 **기사 길이가 중요도를 결정**하게 됩니다.
3. **MECE + 도구 차원의 이중 안전장치.** `score >= 2` / `score < 2`는 논리적으로 상호배타·전수입니다. 그런데도 Route B를 **Fallback route**(n8n은 Fallback Output)로 지정했습니다. 이유는 — 두 필터를 각각 쓰면 수식 오타나 `score`가 예상 밖의 빈 값일 때 **양쪽 모두 통과 못 해 데이터가 조용히 사라집니다.** Fallback은 "앞선 모든 경로가 막히면 반드시 실행"을 도구가 보장하므로 유실 확률이 구조적으로 0이 됩니다.
4. **비대칭 출력이 의도다.** CORE만 알림을 보냅니다. 알림 채널의 가치는 신호/잡음 비율이므로, 참고 등급까지 알리면 채널 자체가 무력화됩니다. REF는 시트에만 축적해 주간 단위로 되돌아봅니다.

# 항목 3 — 핵심 기술 원리 적용

## Q4. Trigger와 Action의 차이를 예시와 함께 설명해 주세요. 왜 Trigger가 "시작점"이고 Action이 "처리"입니까?

**[30초 답변]**
> Trigger는 **"언제 실행할지를 결정하는 유일한 지점"** 이고, Action은 **"주어진 데이터를 변환·전달하는 지점"** 입니다. 결정적 차이는 **호출 방향**입니다. Trigger는 워크플로우가 외부 세계에 "변화 있었나?"를 묻거나 외부가 워크플로우를 깨우는 쪽이고, Action은 워크플로우가 외부에 "이걸 해줘"라고 지시하는 쪽입니다. 그래서 Trigger는 워크플로우에 정확히 하나이고, Action은 여럿일 수 있습니다.

**[확장 답변]** — 제 구현으로 설명

| | Trigger (RSS Watch / Schedule) | Action (Sheets Add a Row / HTTP POST) |
|---|---|---|
| 호출 방향 | 외부 상태를 **관찰** (또는 외부가 나를 깨움) | 외부에 **명령** |
| 입력 | 없음 — 스스로 시각과 상태를 근거로 발화 | 이전 단계의 출력 |
| 상태(state) 보유 | **있음** — "어디까지 처리했는지" 기억 | 없음 — 매 호출이 독립적 |
| 개수 | 워크플로우당 **1개** | 제한 없음 |
| 실패의 의미 | 워크플로우 전체가 시작되지 않음 (조용한 실패) | 해당 단계만 실패, 나머지는 진행 가능 |
| 재실행 | 재실행 개념이 없음 (다음 폴링을 기다림) | 재시도 가능 |

**"Trigger가 상태를 갖는다"가 핵심입니다.** 이걸 이해하지 못하면 실제 사고가 납니다. 제 n8n 구현에서 처음에 `Schedule Trigger + RSS Read` 조합을 썼더니 **매 실행마다 25건 전량이 시트에 다시 쌓였습니다.** `RSS Read`는 Action이라서 상태가 없고, "무엇이 신규인지 기억하는 책임"이 아무에게도 없었기 때문입니다. `RSS Feed Trigger`(진짜 Trigger)로 교체하니 해결됐습니다.

Make가 상태 저장 트리거에 `Watch` 접두어를 붙여 규약화한 것도 같은 이유입니다 — **`Watch`는 "내가 기억한다"는 선언**입니다.

**한 문장 정리**: Trigger는 *시간과 상태*를 다루고, Action은 *데이터*를 다룹니다.

## Q5. 비교한 도구들의 차이를 "업무 요구사항" 관점으로 연결해 설명해 주세요 (협업/운영/디버깅/확장/비용).

**[30초 답변]**
> 두 도구의 차이는 기능 유무가 아니라 **"어떤 비용을 누가 지불하는가"의 배치 차이**였습니다. Make는 인증·호스팅·가용성 비용을 플랫폼이 지불하고 사용자는 실행량과 데이터 위치를 내줍니다. n8n은 사용자가 인증·호스팅·상태관리 비용을 지불하고 실행량 한계비용과 데이터 주권을 얻습니다. 그래서 도구 선정은 **업무 요구사항을 비용 항목으로 번역하는 작업**이 됩니다.

**[확장 답변]** — 요구사항 → 비용 항목 → 도구

| 업무 요구사항 | 번역된 비용 항목 | 우세 도구 | 정량 근거 |
|---|---|---|---|
| **협업** — 비개발자에게 인수인계해야 함 | 문서화 비용 | **Make** | 캔버스와 History가 그대로 문서. n8n Community는 워크플로우·자격증명에 **인스턴스 소유자와 생성자만 접근** 가능해 공유 자체가 막힘 |
| **운영** — 내가 없어도 돌아야 함 | 가용성 비용 | **Make** | 관리형 24/7. n8n 로컬 셀프호스팅은 PC 절전 시 트리거 미발화 → 상시화하려면 VPS 비용 발생 |
| **디버깅** — 정규식·파싱을 반복 개선해야 함 | 시행착오 비용 | **n8n** | Pin Data로 입력을 고정한 반복 테스트가 무료. Make는 재실행마다 오퍼레이션 소모 |
| **확장** — 처리량이 수천 건으로 늘어남 | 한계비용 | **n8n** | Make Free 월 1,000 오퍼레이션. 10건·15분 간격이면 월 2,880으로 초과. n8n은 실행 과금 없음 |
| **확장** — 분기 규칙이 12개 → 30개로 늘어남 | 유지보수 비용 | **n8n** | 키워드 1개 추가 = Make는 400자 수식 2곳 수정, n8n은 배열에 문자열 1개 추가 |
| **비용** — 월 실행 1,000회 이하 | 총소유비용 | **Make** | 무료 플랜 내 0원. n8n은 상시 구동 인프라 비용 발생 |
| **보안** — 사내·개인정보를 다룸 | 데이터 주권 비용 | **n8n** | 데이터·자격증명이 자체 인프라를 벗어나지 않음 |

**핵심은 "3승 4패"가 아니라 가중치입니다.** 같은 사람이 만든 두 자동화가 서로 다른 도구를 요구했다는 사실이 그 증거입니다 — 프로젝트 1(리서치 큐레이션)은 하루 놓쳐도 다음 날 회복되지만, 프로젝트 2(공시 레이더)는 가동 중단이 곧 그날의 관측 공백 — 복구 불가능한 손실입니다. **요구사항의 실패 비용이 다르면 가중치가 다르고, 가중치가 다르면 도구가 달라집니다.**

## Q6. 프로젝트 2에서 이 도구를 선택한 이유를 비교 항목 2개 이상과 연결해 설명해 주세요.

**[30초 답변]**
> Make를 선택했고, 비교 항목 **⑧ 호스팅·가동 지속성**, **⑤ 실행 로그·디버깅**, **③ 무료 플랜 예산** 3개가 근거입니다. 이 업무의 실질 손실은 "느림"이 아니라 **"관측 공백"** — 확인하지 않은 날의 공시를 놓치는 것 — 이라서 매일 빠짐없는 가동이 요구사항이고, 시그널 사전은 운영하며 계속 다듬어야 해서 API 응답 원문과 분류 결과를 함께 남기는 실행 이력이 개선 데이터가 되며, 활성 시나리오 2개·오퍼레이션 예산을 P1과 합쳐 정확히 무료 한도 안에 들어오도록 설계했습니다.

**[확장 답변]**

**근거 ① 항목 ⑧ 가동 지속성 (결정적)**
n8n Community를 로컬에서 돌리면 노트북 절전 시 실행되지 않습니다. 프로젝트 1에서 이 특성을 실제로 확인했습니다. 리서치 큐레이션은 하루 건너뛰어도 다음 실행에서 회복되지만, 공시 레이더는 **하루를 건너뛰면 그날의 관측이 영구 공백**이 됩니다 — §1.2에서 As-Is의 실질 손실을 '관측 공백'으로 정의했으므로, 가동 중단은 곧 요구사항 위반입니다. 로컬 셀프호스팅은 이 업무에 부적합합니다.

**근거 ② 항목 ⑤ 실행 로그 (운영)**
이 워크플로우의 핵심 자산은 시그널 사전 12개이고, 신유형 공시가 나오면 사전을 갱신해야 합니다. 오분류는 **조용합니다**(ROUTINE으로 분류되어 넘어감). Make History는 HTTP 모듈의 **응답 원문(공시 목록 JSON)과 분류 모듈의 출력을 함께** 보관하므로 "왜 이 공시가 SIGNAL로 안 잡혔는가"를 원문과 대조해 역추적할 수 있습니다. ROUTINE 시트를 주간 리뷰하는 것이 곧 사전 개선 백로그가 됩니다.

**근거 ③ 항목 ③ 무료 플랜 예산 (정합성)**
P2는 평일 13오퍼레이션 × 22일 ≈ 월 294로 설계했고, P1의 540과 합쳐 834/1,000 — **활성 시나리오 2개, 오퍼레이션 84%로 무료 한도를 정확히 소진하는 포트폴리오 설계**입니다. 역으로, 이 업무는 로직이 키워드 매칭 1단계로 단순해서 n8n의 강점(비교 항목 ⑦ Code 노드 표현력)이 발휘될 여지가 없습니다 — **n8n이 이기는 축이 무의미한 업무**라는 점도 Make를 뒷받침합니다.

**감수한 트레이드오프도 말씀드립니다.** 오퍼레이션 과금(월 약 294), 활성 시나리오 2개 한도 소진, API 키가 Make 클라우드에 저장된다는 점입니다. 마지막 항목은 DART 키가 **공시 조회 전용(개인정보 접근 없음)** 이라 위험도가 낮고, 노출 시 재발급으로 즉시 무효화된다는 점으로 수용 가능하다고 판단했습니다 — 물론 스크린샷에서는 전부 마스킹합니다.

**추가로, P1과의 구조적 차별화도 의도된 선택입니다.** P1은 상태 저장형 Watch 트리거에 멱등성을 위임했지만, P2는 HTTP 폴링이라 트리거가 아무것도 기억해 주지 않습니다. 그래서 **질의 자체를 멱등하게** 만들었습니다 — 매일 08:00에 "전일 하루" 창을 조회하면 같은 날 몇 번을 실행해도 같은 결과가 나오고, 실행 시각 이후 접수되는 공시를 놓치는 문제도 없습니다. 같은 개념(멱등성)을 두 방식으로 풀어본 것이 이 조합의 학습 가치입니다.

# 항목 4 — 심층 인터뷰

## Q7. 트리거가 불안정하거나 외부 연동이 자주 실패한다면 모니터링 / 재시도 / 대체 경로를 어떻게 설계하겠습니까?

**[30초 답변]**
> 실패를 **3가지로 분류**해서 각각 다르게 다룹니다. ① **조용한 실패**(트리거가 아예 안 돎) ② **일시적 실패**(429/5xx·타임아웃) ③ **영구적 실패**(401 인증 만료·404). 조용한 실패는 재시도로 잡을 수 없어 **하트비트 감시**가 필요하고, 일시적 실패는 **지수 백오프 재시도**, 영구적 실패는 즉시 사람에게 에스컬레이션 + **대체 경로로 데이터를 보존**합니다.

**[확장 답변]**

### ① 모니터링 — 실패 유형별로 감지 방법이 다르다

| 실패 유형 | 감지 방법 | 구현 |
|---|---|---|
| Action 실패 (예외 발생) | 도구의 오류 알림 | Make: 시나리오 설정 → 오류 시 이메일 알림 ON / n8n: Error Trigger 워크플로우 |
| **조용한 실패 — 트리거 미발화** | **하트비트(Dead man's switch)** | 매 실행 종료 시 Sheets `_heartbeat` 시트에 타임스탬프 1행 기록. **별도 감시 시나리오**가 하루 1회 최신 타임스탬프를 확인해 26시간 이상 갱신이 없으면 Discord 경보 |
| 부분 실패 — 데이터는 통과했으나 결과가 이상 | **품질 지표 감시** | CORE 비율이 0% 또는 100%로 3일 연속 고정되면 스코어링 이상 신호로 경보 |

**하트비트가 핵심입니다.** 트리거가 안 돌면 실행 기록 자체가 없어서 도구의 오류 알림이 작동하지 않습니다. **"없어야 할 것이 없음"은 감지할 수 없고, "있어야 할 것이 없음"만 감지할 수 있습니다.** 그래서 성공 기록을 남기고 그 부재를 감시합니다.

### ② 재시도 — 재시도해도 되는 실패만 재시도한다

| 오류 | 재시도 여부 | 정책 |
|---|---|---|
| 429 Rate limit | ✅ | 지수 백오프 (2s → 8s → 32s), 최대 3회 |
| 500·502·503, 타임아웃 | ✅ | 동일 |
| 401·403 (인증 만료·권한) | ❌ | 즉시 중단 + 사람 에스컬레이션. 재시도는 부하만 늘림 |
| 400 (페이로드 오류) | ❌ | 코드 결함. 재시도하면 영구 실패 |
| 404 | ❌ | 대상이 없음. 대체 경로로 |

- **Make**: HTTP 모듈 뒤 `Error handler` → `Break` 지시자를 붙이면 **자동 재시도 큐**에 들어가 시나리오 설정의 재시도 정책에 따라 반복됩니다. 시나리오 설정에서 `Sequential processing`을 켜면 순서 보장도 가능합니다.
- **n8n**: 노드 Settings에 `Retry On Fail` + `Max Tries` + `Wait Between Tries` 옵션이 노드 단위로 있습니다.

**재시도는 반드시 멱등성과 함께 설계해야 합니다.** Sheets 적재 후 Discord가 실패해 전체를 재시도하면 시트에 중복 행이 생깁니다. 그래서 제 워크플로우는 **Sheets 적재 → Discord 알림** 순서입니다. 알림 재시도가 데이터를 오염시키지 않습니다. 순서를 뒤집으면 알림이 두 번 갈 수 있는데, 중복 알림은 중복 데이터보다 복구가 쉽습니다. **재시도 설계는 "무엇을 두 번 해도 안전한가"를 먼저 정하는 일입니다.**

### ③ 대체 경로 — 데이터는 잃지 않는다 (Degrade, don't fail)

```
정상 : RSS → 스코어링 → 분기 → [Sheets + Discord]
1차 대체 : Sheets 실패 → _quarantine 시트에 원본 JSON 적재 → 복구 후 재처리 배치
2차 대체 : Discord 실패 → Gmail로 동일 내용 발송 (채널 이중화)
3차 대체 : 둘 다 실패 → Make Data Store에 큐잉 후 다음 실행에서 재발행
최종     : RSS 피드 자체가 죽음 → 보조 피드(TechCrunch 등)로 폴백 + 소스 변경 경보
```

원칙은 **"실패하지 않게 만드는 것"이 아니라 "실패해도 데이터를 잃지 않게 만드는 것"** 입니다. 100% 가용성은 개인 무료 플랜으로 달성할 수 없지만, **유실 0은 달성할 수 있습니다.** 알림은 늦어도 되지만 데이터는 사라지면 복구가 불가능합니다 — 이 비대칭성이 우선순위를 정합니다.

### ④ 이번 구현에 이미 들어간 안전장치
- **Fallback route / Fallback Output** — 분기 조건 오류 시에도 데이터 유실 0
- **status=013(데이터 없음) 정상 흐름 처리** — 공시 없는 날을 오류가 아닌 조기 종료로 설계 (P2)
- **트리거 상태 저장 위임** — 중복 적재 차단
- **`title_safe` 사전 생성** — 특수문자로 인한 Discord 400 예방 (사후 대응이 아닌 사전 차단)

## Q8. 조건 분기 규칙이 늘어나거나(2개 → 5개) 처리 로직이 복잡해진다면 워크플로우를 어떻게 구조화·모듈화하겠습니까?

**[30초 답변]**
> 분기를 늘리지 않습니다. **분기 개수를 늘리는 대신 "판정"과 "실행"을 분리**합니다. 지금도 Router가 하는 일은 `score` 하나를 보는 것뿐이고, 판정 로직은 그 앞의 스코어링 단계에 있습니다. 규칙이 5개가 되면 스코어링 단계가 `route` 값 하나(`A`~`E`)를 계산하고 Router는 그 값으로만 갈라집니다. 그리고 **규칙 자체를 워크플로우 밖의 Google Sheets 룰 테이블로 외부화**해서, 규칙 추가가 워크플로우 수정이 아니라 **행 추가**가 되게 만듭니다.

**[확장 답변]**

### 원칙 1. 판정과 실행의 분리 (Decision / Execution Split)

```
❌ 나쁜 확장:  Router에 조건 5개 → 각 경로에 Action 3개씩 = 15개 모듈, 조건식이 5곳에 흩어짐
✅ 좋은 확장:  [판정 모듈] route 값 1개 계산 → Router가 route로만 분기 → 경로별 Action
```

Router의 필터에 복잡한 조건식을 넣으면 **비즈니스 규칙이 도구 UI 안에 갇힙니다.** 테스트도 불가하고 diff도 안 됩니다. 판정을 한 곳(Code 노드 / Set 모듈)에 모으면 그 부분만 단위 테스트할 수 있습니다 — 이번에도 `_test_scoring.js`로 그렇게 했습니다.

### 원칙 2. 규칙의 외부화 (Rule Table)

키워드 사전과 임계값을 워크플로우 안에 하드코딩하면, 규칙 하나 추가가 수식 수정이 됩니다. Google Sheets에 룰 테이블을 두면:

| rule_id | 범주 | 키워드 | 가중치 | 활성 |
|---|---|---|---|---|
| R01 | 자본시장 | 인수 | 2 | Y |
| R02 | 제도정책 | 규제 | 1 | Y |
| R03 | 기술자산 | 특허 | 2 | N |

워크플로우는 시작 시 룰 테이블을 읽어 점수를 계산합니다. → **규칙 추가 = 행 추가**. 워크플로우를 건드리지 않으므로 회귀 위험이 없고, 비개발자도 규칙을 바꿀 수 있고, 시트 자체가 규칙 변경 이력이 됩니다.
비용: 룰 조회 오퍼레이션 1회 추가. 규칙이 5개를 넘어가면 이 비용은 즉시 회수됩니다.

### 원칙 3. 서브워크플로우로 계층 분리

```
[Orchestrator]  수집 → 정규화 → 판정 → route별 디스패치
      ├─ [Sub: Notify]   알림 채널 전략 (Discord/Gmail 폴백 포함)
      ├─ [Sub: Archive]  저장 전략 (Sheets/격리 시트)
      └─ [Sub: Escalate] 사람 개입 요청
```

Make는 `Make: Run a scenario` 모듈, n8n은 `Execute Sub-workflow` 노드로 구현합니다.
**분리 기준은 "변경 주기가 다른 것을 같은 파일에 두지 말라"** 입니다. 알림 채널은 자주 바뀌고 저장 스키마는 거의 안 바뀝니다. 변경 주기가 다르면 분리합니다.
단, Make Free는 활성 시나리오 2개 제한이 있어 서브시나리오 분리 자체가 유료 기능이 됩니다. **이 지점이 무료 노코드의 실질적 천장이고, n8n 셀프호스팅으로 넘어갈 두 번째 이유입니다.**

### 원칙 4. 분기 폭발을 곱셈에서 덧셈으로

조건이 독립적으로 3개(중요도 3단계 × 카테고리 4종 × 채널 2개)면 경로가 24개가 됩니다. 이건 Router로 풀 문제가 아닙니다.
→ 판정 단계에서 `{tier, category, channels[]}` 를 계산하고, **디스패치는 매핑 테이블 조회**로 처리합니다. 경로 수가 `3×4×2`(곱셈)에서 `3+4+2`(덧셈)로 떨어집니다. 노코드 캔버스에서 곱셈적 분기는 반드시 관리 불가능해집니다.

### 원칙 5. 복잡도 임계선을 미리 정해 둔다
아래 중 **2개 이상**에 해당하면 노코드 안에서 버티지 않고 코드로 이전합니다.

- 조건 분기 5개 초과
- 수식 하나가 200자 초과
- 같은 규칙이 2곳 이상에 중복 기술됨
- 단위 테스트 없이 배포하기 두려움
- 실행 1회의 모듈 수가 20개 초과

**"언제 도구를 바꿀지"를 미리 정해 두는 것 자체가 설계**입니다. 그 선이 없으면 항상 늦게 옮기게 됩니다.

## Q9. 노코드 자동화로는 한계가 있는 업무 1가지를 들고, 그 이유와 "코딩 기반 자동화의 확장 아이디어"를 설명해 주세요.

**[30초 답변]**
> **공시 원문에서 계약 상대방·계약 금액·기간 같은 딜 조건을 구조화 추출하는 업무**입니다. 프로젝트 2에서 실제로 막힌 지점입니다 — 제 레이더는 "공급계약 공시가 났다"는 **발생 사실**까지만 잡고, "누구와 얼마짜리 계약인가"는 원문(표 중심의 XML/HTML 문서) 안에 있어 노코드로는 닿지 않습니다. 이유는 3가지입니다 — ① 입력이 **레이아웃 정보를 가진 비정형 문서**라 필드 매핑 패러다임에 안 맞고, ② 기업·서식마다 표 구조가 달라 **정답 없는 반복 개선**이 필요한데 노코드는 단위 테스트가 불가능하고, ③ 추출 결과의 **신뢰도를 정량 평가**할 수단이 없습니다. 코드 기반으로 가면 파서를 **테스트 가능한 함수로 분리**하고, 노코드는 오케스트레이션만 담당하는 **하이브리드**로 갑니다.

**[확장 답변]**

### 왜 이 업무가 노코드의 한계인가

| 한계 | 구체적 이유 |
|---|---|
| **입력 구조** | 공시 원문은 셀 병합·다단·각주가 섞인 표 중심 문서(XML/HTML)다. 노코드의 "필드 → 필드" 매핑 모델은 1차원 레코드를 전제한다. 표의 좌표·병합 정보를 다룰 표현 수단이 없다 |
| **반복 개선 불가** | 기업·서식 유형마다 표 구조가 다르므로 30개 공시 원문으로 회귀 테스트를 돌려야 한다. 노코드에는 테스트 스위트·CI 개념이 없다. 개선했는데 다른 서식이 깨져도 **알 수 없다** |
| **신뢰도 측정 불가** | "추출 정확도 92%"를 계산하려면 정답셋과 자동 평가 루프가 필요하다. 노코드로 평가 파이프라인을 만드는 것은 본래 목적보다 복잡해진다 |
| **비용 구조 역전** | 원문 1건에 표 수십 개면 노코드에서는 모듈 실행이 수백 회로 폭발한다. Make Free 월 1,000 오퍼레이션을 **원문 몇 건이 소진**한다 |
| **버전 관리 부재** | 파싱 규칙은 계속 바뀐다. 무엇을 왜 바꿨는지 diff로 볼 수 없으면 규칙이 부채가 된다 |

**일반화하면**: 노코드는 **"입력 스키마가 안정적이고, 규칙이 짧고, 실패가 눈에 보이는"** 업무에서 강합니다. 이 업무는 세 조건을 모두 위반합니다.

### 코드 기반 확장 아이디어 — 하이브리드 아키텍처

**핵심 판단: 노코드를 버리는 게 아니라, 노코드를 오케스트레이션 계층으로 격하시키고 판단 로직을 코드로 내린다.**

```
[노코드 계층 — Make]           책임: 이벤트 감지 · 라우팅 · 사람 인터페이스
   DSR-v1이 SIGNAL 공시 감지 (rcept_no 확보)
        │  HTTP POST (rcept_no + report_nm)
        ▼
[코드 계층 — Python / FastAPI on Cloud Run]   책임: 원문 파싱 · 신뢰도 산출
   1. DART 원문 API로 공시 문서 수신 → 표 추출 (좌표·병합 정보 유지)
   2. 규칙 기반 1차 파싱 → 계약 상대방 / 금액 / 기간 / 조건
   3. 실패 셀만 LLM 구조화 추출로 폴백 (비용 최소화 — 전량 아님)
   4. Pydantic 스키마 검증 + confidence 산출
   5. confidence < 0.8 → needs_review = true
        │  JSON 응답
        ▼
[노코드 계층 — Make]           책임: 결과 분배
   confidence >= 0.8 → Sheets(딜 조건 테이블) 적재 + SIGNAL 알림에 상세 첨부
   confidence <  0.8 → Discord에 "사람 확인 필요" + 원본 링크
        │
        ▼
[피드백 루프]  사람이 교정한 값을 정답셋에 축적 → 회귀 테스트 케이스로 승격
```

**이 설계의 3가지 판단**

1. **경계를 "판단의 복잡도"로 그었다.** 이벤트 감지·알림·기록은 노코드가 압도적으로 저렴합니다. 파싱과 신뢰도 산출만 코드로 내립니다. 전부 코드로 옮기면 스케줄링·공시 감시·알림 채널을 직접 구현해야 하는데, 그건 이미 잘 풀린 문제를 다시 푸는 낭비입니다.
2. **LLM을 1차 수단이 아니라 폴백으로 뒀다.** 전량 LLM 추출은 비용·지연·비결정성이 모두 나쁩니다. 규칙 기반으로 80%를 처리하고 실패 셀만 LLM에 보내면 비용이 한 자릿수 퍼센트로 떨어지고, **어디서 규칙이 부족한지가 로그로 남습니다.**
3. **`confidence`와 `needs_review`를 1급 출력으로 만들었다.** 자동화의 성숙도는 "얼마나 자동으로 하는가"가 아니라 **"자동으로 하면 안 될 때를 아는가"** 로 측정됩니다. 사람 개입을 예외가 아니라 설계된 경로로 둡니다.

**검증 가능성이 진짜 이득입니다.** 코드로 내리면 `pytest`로 30개 공시 원문 회귀 테스트를 돌릴 수 있고, 정확도를 숫자로 보고할 수 있고, 사람 교정 데이터가 테스트 케이스로 승격됩니다. 노코드에서는 이 루프가 원리적으로 만들어지지 않습니다.

**이번 과제에서 얻은 것을 한 문장으로**: 노코드는 "코딩을 안 하는 방법"이 아니라 **"어디까지가 코딩이 필요 없는 영역인지 판별하는 훈련"** 이었습니다. 그 경계를 정확히 아는 것이 두 방식 모두를 쓸 수 있게 만듭니다.

# 예상 추가 질문

## Q10. 왜 Zapier를 쓰지 않았습니까?
> Zapier 무료 플랜은 **월 100 태스크 + 2단계 Zap(트리거 1 + 액션 1)** 만 허용하고 멀티스텝·Filter·Paths가 유료입니다. 이 과제의 필수 요구사항인 "Action 2개 이상 + 조건 분기 1개 이상"을 **무료로는 구조적으로 충족할 수 없습니다.** 14일 Pro 트라이얼로는 가능하지만 종료 후 워크플로우가 정지해 재현 검증이 불가능해지고, 과제의 "과금 리스크 완화 가이드"에도 어긋납니다. 그래서 무료로 전 요구사항을 만족하는 Make + n8n을 선택했습니다.

## Q11. 무료 한도를 넘으면 어떻게 합니까?
> 3단계입니다. ① **먼저 예산 내로 설계** — 이번에는 처리 건수와 폴링 주기를 오퍼레이션 예산에서 역산했습니다(P1 540 + P2 약 294 = 약 834/1,000). ② **한도 근접 시 구조 최적화** — P2는 공시 없는 날을 status 필터로 1오퍼레이션 조기 종료시켜 이미 빈 실행 비용을 최소화했고, P1은 트리거 폴링을 Webhook 푸시로 바꾸면 실제 이벤트 건수만 소모됩니다. ③ **그래도 부족하면 워크로드 이전** — 상시 가동이 필요 없는 P1을 n8n 셀프호스팅으로 옮기면 Make 예산이 통째로 비워집니다. **유료 전환은 세 단계를 다 쓴 뒤의 선택지**입니다.

## Q12. 같은 기사가 두 번 기록되지 않는다는 걸 어떻게 보장합니까?
> dedup key를 `link`로 정하고, 신규 판정 책임을 **폴링 트리거의 상태 저장**에 위임했습니다. Make `Watch RSS feed items`와 n8n `RSS Feed Trigger`가 마지막 처리 지점을 인스턴스에 저장합니다. 검증은 시트의 `링크` 열 중복 여부로 합니다. 실제로 n8n에서 `Schedule + RSS Read` 조합을 썼을 때 25건이 매일 중복 적재됐고, 그 경험으로 이 계약을 명세에 명시했습니다.

## Q13. 이 자동화가 만든 실질적 가치는 무엇입니까?
> 시간 절감은 부수 효과입니다(P2 기준 연 약 17시간). 실질 가치는 두 가지입니다. ① **판단 기준의 명문화** — "무엇이 중요한가"를 키워드 12개와 임계값 2로 외부화했습니다. 기준이 문서화되면 나중에 반박하고 개선할 수 있습니다. 머릿속 기준은 그럴 수 없습니다. ② **관측 공백 제거와 1차 자료 우위** — P2에서 확인하지 않은 날의 공시는 영구히 놓친 관측이고, 매일 자동 수집 + Fallback route로 유실 확률을 구조적으로 0으로 만들었습니다. SIGNAL 시트에 쌓이는 기업별 전략 이벤트 타임라인은 산업 분석의 1차 데이터셋이 됩니다.

## Q14. 민감정보는 어떻게 관리했습니까?
> ① Discord Webhook URL과 Google 서비스 계정 Private Key는 **스크린샷에서 마스킹**하고 문서에는 `***MASKED***`로 표기했습니다. ② 서비스 계정 키 JSON 파일은 제출물에 포함하지 않았습니다. ③ 계정 이메일은 일부 가림 처리했습니다. ④ P2의 DART API 키(crtfc_key)는 URL 쿼리 파라미터로 전달되므로 HTTP 모듈 캡처 시 반드시 마스킹했습니다. ⑤ 설계 차원에서도 — P2가 다루는 데이터는 전부 공개 공시 정보라 민감 데이터가 애초에 파이프라인에 없고, API 키도 공시 조회 전용이라 노출 시 재발급으로 즉시 무효화됩니다. 마스킹은 사후 조치이고, 다루는 데이터의 민감도를 낮게 설계하는 것이 근본 조치입니다.
